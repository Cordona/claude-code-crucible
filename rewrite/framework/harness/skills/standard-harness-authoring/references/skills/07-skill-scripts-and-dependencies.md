# 07 · Scripts and dependencies (SCR)

Purpose: bundled scripts and external tools work on a fresh machine, from any directory, and say exactly what happened; what the human sees is a script's compact view, relayed as printed. A script's `--help` is the single source of truth for the caller's contract: what it is, how to call it, what comes back and what it depends on; a skill that calls it never restates it. The caller reads it once, before the first use in a session.
Judges script interfaces, error handling, side-effect safety, dependencies and the views shown to the human (SCR-16–SCR-23: a script prints every view, built on core's human-view library, never formatting a list, path or Data section by hand); mode bits, strict mode, prompts and paths are lint; a `--help` page's first line and size are `help-check.sh`'s (lint spec, section J).

**Applies when:** the skill bundles or calls scripts; SCR-07 also when its body has the agent invoke an external tool (CLI, MCP server, plugin, companion agent or skill); SCR-16–SCR-23 also when the skill, or a script it bundles or calls, shows the human a view (any output the human reads: a gate, a plan, a summary, an error to act on; an AskUserQuestion's question and option labels are not a view: the main thread composes them, never in place of a view the step owes; a view is never put inside a question, whose text shows no Markdown or line breaks).
**Context:** human-view's Layout rules (`${CLAUDE_CONFIG_DIR:-$HOME/.claude}/skills/human-view/SKILL.md`): SCR-18–SCR-23 are judged by those rules, exceptions included; read them in full before judging a view.
**MUST lint:** LNT-28, LNT-30, LNT-47.

**Levels.** Each item takes the level of the heading above it.

## MUST

- **SCR-01** · Does SKILL.md name each script, tell the reader to run its `--help` once, before the first use in a session, and not again in that session unless the contract is no longer in its context (after a compaction), and in each step name only the command it runs and the output or exit it acts on? For a script that serves per-command pages (SCR-15), does it cite `<script> <cmd> --help` the same way, once per command it runs? When the skill's reader never runs the script (a dispatched agent, say), does it only name who runs it and cite its `--help` as the contract? · Check: FAIL if a table or prose restates a script's contract (its commands, outputs, exit codes, dependencies or runtime), or if a command the skill runs on a per-command-page script has no `<script> <cmd> --help` citation, or if it claims the page holds what the page doesn't (a stale citer); a script that gains per-command pages updates every citer (grep the search roots) in the same change. For a reader who never runs it, describing what that reader receives (a rejection message, say) passes only as what the reader sees, never as the script's output format. · Fix: replace it with "run `<script> --help` once, before the first use in a session: it is the full contract"; for per-command pages, "run `<script> <cmd> --help` once, before the first use of `<cmd>` in a session"; for a reader who never runs it, "`<runner>` runs `<script>`; its `--help` is the full contract".
- **SCR-05** · Are scripts idempotent, do destructive or stateful ones default to dry-run or need an explicit flag, and does none delete another party's output without a backup? · Check: read every write and delete path. · Fix: add `--apply`/`--confirm`; default to dry-run; move instead of delete.
- **SCR-07** · Does SKILL.md list only what the agent itself calls — CLIs, MCP servers, plugins, companion agents and skills — each with a one-line install/setup hint, a version floor where behavior depends on one, and the step when it is missing (a missing seat stops, SUB-06); and does each script list its own tools in its `--help`, not in SKILL.md, and check them at start, right after handling `--help`, exiting with the missing one named? · Check: also, where a path or interpreter may vary, the skill runs the script once for its `usage:` line before first use; text-parsing scripts set UTF-8 I/O; FAIL a dependency check that runs before `--help` prints, since the page must print where a tool is missing (lint spec, section J). · Fix: list the agent's own tools in SKILL.md; move a script's tools into its `--help`; add `command -v x || { echo "x missing: install …" >&2; exit N; }` after the `--help` branch.
- **SCR-16** · Is every view the human sees printed by a script and relayed word for word, the skill composing, counting, summarising, rewording or prefacing nothing, except a fixed one-line notice the skill spells out word for word? · Check: FAIL a step that has the model write or reshape a view (a hand-counted summary, a lead-in line, a table built from a script's output) or give a notice by its gist; a notice's placeholder passes only for a value copied whole (a path, a name). · Fix: move the view into a renderer script built on human-view (`view.jq`, `paths.jq`); have the step relay its output word for word.

## SHOULD

- **SCR-02** · Does each script validate input first (a malformed call errors and writes nothing), handle edge cases itself, and parse model-written text tolerantly but by tag position? · Check: read the argument and parse code. · Fix: add an early validation block that exits with usage before any write.
- **SCR-03** · Do error messages say what failed, what was expected, and what to try next? An agent given a bare error retries the same call or improvises a workaround. · Check: read every error path. · Fix: "<what>; expected <x>; try <y>".
- **SCR-04** · Is output structured on stdout with diagnostics on stderr, size-bounded with a truncation notice, and are exit codes distinct and documented in `--help` (not in SKILL.md)? · Check: read. · Fix: JSON/TSV to stdout; "showing N of M"; list exit codes in `--help`.
- **SCR-06** · Is every constant (timeout, limit, magic number) explained? The next editor or agent, unable to tell a measured limit from a guess, retunes an unexplained one. · Check: read. · Fix: add a one-line reason beside it.
- **SCR-08** · Do script paths resolve independent of the current directory — `${CLAUDE_CONFIG_DIR:-$HOME/.claude}/skills/<name>/` in skills run by or preloaded into agents, `${CLAUDE_SKILL_DIR}` only in `!` lines and Skill-tool or slash invocations? · Check: judge beyond LNT-37 (bare relative paths), including how scripts find siblings. · Fix: use the matching form; resolve siblings from the script's own dir.
- **SCR-09** · Is logic every run would rewrite, and every hard-to-type command, bundled as a tested script? · Check: yes if no step asks the agent to compose a multi-line command or helper each run. · Fix: move it into `scripts/<verb>.sh`.
- **SCR-10** · Are child processes and temp state cleaned up on every exit path? · Check: judge beyond LNT-32 (`mktemp` + `trap`). · Fix: kill children and remove state in the `EXIT` trap.
- **SCR-11** · Does every entry-point script's `--help` hold the caller's contract: usage lines, a purpose, one line per option, the output callers parse (SCR-14), exit codes (SCR-13) and dependencies? With per-command pages (SCR-15), does the top page hold every usage line (another script may read them), the purpose, a `Commands:` index and the facts no single command owns, and each command page that command's options, parsed output, exit codes and dependencies? · Check: judge beyond LNT-27, LNT-74 and LNT-75; read every page. Throughout SCR-11–SCR-15: a caller is a skill, agent or script that runs the script (grep the search roots for its name; read each call); a line is one list entry, which may wrap with its continuation indented (80 columns preferred, for prose only); the purpose is the one paragraph after the usage lines, which may wrap at column 0 and carry page-wide guarantees; on a usage line `<script>` may follow `sh` or `bash`. FAIL an option without its own line (a usage line is not one), except `--help`, whose `-h` goes on the top page's `<script> --help` usage line only. An environment variable a caller or the human may set is an option, its line giving its default, even a default shown inside a path; it needs no line when it only sets an option's default shown on that option's line, or when a shared lib owns it and the page points to the page stating its rules (also where an exit entry names it). FAIL a placeholder two options share used bare for one of them; a statement about all of them passes. · Fix: add each missing part as one line; name the option.
- **SCR-12** · Does each page state guarantees, not mechanism? A guarantee is what callers may rely on (what remains after exit, what is never touched or read, what is atomic), with its known limit (a race, a SIGKILL) as one clause. · Check: FAIL a sentence without which no caller would call, branch, retry or relay differently: rationale, history, internals (temp files, write steps, recipes, which missing tool sends which exit), timings, rules the scripts it checks must meet. FAIL a guarantee missing a known limit; a write guarantee not naming what remains after exit and what is never touched; a fact stated twice; "nothing else is written", "writes only X" or "Writes: nothing." when temp files are written; a shared fact (a dependency hint, a constant's unit) worded differently on sibling pages of one skill or flow; a shape or rule another file owns (a schema, a field table, a URL grammar, a refusal list) restated, unless the page prints it from its owner at run time, or a caller relies on the listing (a step needs the rule to choose a value and no file the caller reads states it; a caller's claim that the page lists it is a stale citer, SCR-01) and a code comment beside the copy names its source. · Fix: move what explains the code beside it into a code comment (a checked script's rule there or into its standard), and drop the rest (timings, measurements, history, notes on what the page leaves out); after what the script writes, if anything, write "Nothing else is left behind (a SIGKILL aside)."; cut the repeat; reuse the sibling wording, printing a constant's unit from the constant; replace a restatement with `see <owner>`, or comment the kept copy with its source.
- **SCR-13** · Is each exit code one line, `<code>  <meaning>; <next step>`, with no causes (stderr names them, SCR-03)? · Check: FAIL a missing next step, or one that isn't what the callers do or doesn't fit every cause the code sends there; where they differ, give the step that fits all (`skip, giving stderr's first line`; `fix what stderr names`), each specific step living in its stderr message. When every caller hands the fault to the human, signal exits (129, 130, 143) included, the step is `show the human stderr, and stop`; a caller that retries gets `fix what stderr names and rerun once, else show the human stderr`. A hook's step is what Claude Code's hook runner does (allow, deny, continue with a context). The one exception to "no causes" is a stderr prefix a caller of that command branches on, stated on that command's page: FAIL it missing, or listed with no such caller. Several on one code: indented sub-lines `<PREFIX>  <meaning>; <next step>` under an entry keeping the default. One sent by several codes: one line before the exit entries, `stderr on exits <codes>: <PREFIX> …; <next step>`, naming every code and any values it carries; those entries then give their meaning only. A hook's deny reasons a caller branches on: one sub-line each, its meaning plus any placeholder value the caller matches; the caller's skill owns the action. · Fix: rewrite each entry in that form; move each cause, with its step, into the stderr message that reports it.
- **SCR-14** · Is output described by what callers do with it: relayed output in one line naming it, each parsed line in its own entry saying what it is and what the caller relies on in it (absolute, its order), never the action on it (exit 0's next step holds that)? Is runtime given only when a plausible call can take over 10 seconds, so the caller waits or runs it in the background? · Check: a caller parses output when a step reads a value out of it to branch on, store or pass as an argument; that includes stderr read field by field (its line shape in one entry) and a file or JSON field a reader (a caller, or the agent it reaches) takes apart (one entry naming its sections and the values readers branch on: `none`, absolute paths, a question's option labels). All other output, one no caller reads included, is relayed. A prefix line SCR-13 states is not described again. FAIL relayed output past one line; a parsed line missing, sharing an entry, lacking what the caller relies on or stating the action; a runtime line on a shorter call. · Fix: `<output>: <what it is>` for relayed output; `<line shape>: <what each field means>` per parsed line; drop other timings.
- **SCR-15** · Does a script serve per-command pages (`<script> <cmd> --help`) only when it has several commands and its one page, trimmed until SCR-11–SCR-14 pass, is still over the LNT-75 ceiling? · Check: FAIL such a page with no per-command pages; per-command pages on a one-command script or one whose trimmed page fits; per-command pages without a top-page usage line exactly `<script> <command> --help` (a literal `<command>`), since `help-check.sh` checks command pages only then; shared text (option, exit-code and dependency lines two pages print; headings and blank lines may repeat) written twice in the source; a stderr message pointing to `--help` that doesn't name the page holding the options. Sizes are LNT-75. · Fix: serve per-command pages, or get a human waiver on LNT-75 (LNT-00); add the declaration line; print shared text from one helper; retarget each such stderr message.
- **SCR-17** · Is the inline view compact (what the human acts on, with no size cap), and is the full view shown only when the human asks: produced by a script, the same for the same input, handed over as its whole absolute path and opened only when the human asks to open it? · Check: FAIL a full view (a whole report, every line of a check) shown unasked, a full view the model builds or reads out, a full view handed over other than as its whole absolute path, or a step that opens it unasked. A raw JSON file's path is an acceptable full view. · Fix: show only the compact view; on the ask, relay the script's path line; open it only on an ask to open it, by script.
- **SCR-18** · Does every view's first line follow Layout rule 1 (light, bold title, optional count; no other icon in the view)? · Check: FAIL a first line breaking rule 1, a light that doesn't match the state, or an icon on any other line. · Fix: print it with `status_line`; drop every other icon.
- **SCR-19** · Do headings, lists and field lines follow Layout rules 2–4? · Check: FAIL a heading, list or field line breaking them (a bullet outside rule 3's exception, a one-item numbered list, a heading with an icon, a zero count shown). · Fix: build them with `section`, `numbered_list`, `bullet_list` and `field_lines`.
- **SCR-20** · Is every path the human may open shown as Layout rule 5 sets? · Check: FAIL such a path shortened, middle-cut or in a code span; a short form passes only for a path cited for recognition inside a line of text. · Fix: print it with `path_text`.
- **SCR-21** · Does every view follow Layout rule 6 (Data last), exceptions included? · Check: FAIL a Data section missing, not last or in another shape, or one on a view with no JSON behind it. · Fix: print it with `data_section`.
- **SCR-22** · Does every view follow Layout rule 7 (no constants)? · Check: FAIL a line whose value no current input changes. · Fix: drop the line.
- **SCR-23** · Does every gate view keep the gate marker Layout rule 8 names, as `open-gate.sh` adds it (`procedure-approval-gate`)? · Check: FAIL a gate view, or a step relaying one, that drops, moves or rewrites the marker, or a renderer that prints it itself; N/A when the skill has no gate. · Fix: pipe the renderer into `open-gate.sh` and relay its output as printed.
