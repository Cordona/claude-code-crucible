# 10 · Hooks (HK)

Purpose: a hook the skill relies on fires, blocks when it should, cannot lock the session, and claims no guarantee it cannot give.
04 decides whether a rule needs a hook; this checklist checks the hook.

**Applies when:** a skill or agent declares `hooks:`, or the skill ships a hook script.
**MUST lint:** LNT-33, LNT-34.

- **HK-01** · MUST · Is a skill-frontmatter hook safe for the rest of the session: (a) scoped by matcher or condition, or `once: true` (which stays registered after a failed or blocking run), and (b) on unrelated events it writes nothing and reads nothing outside the project and skill dirs, so it is safe in an untrusted `-p` run? · Check: report FAIL(a|b). · Fix: narrow the matcher or add a no-op guard.
- **HK-02** · MUST · Is the hook placed where its lifetime fits — agent frontmatter for per-subagent checks (`Stop` becomes `SubagentStop`), skill frontmatter for session checks — never relying on a skill hook firing inside subagents? · Check: read. · Fix: move per-subagent checks into the agent file.
- **HK-03** · MUST · Does the skill claim only what the hook guarantees — silence is not approval, deny holds in every mode, PostToolUse cannot undo, async hooks cannot block, command hooks cannot call tools, `@` files and `/name` bypass PreToolUse (use UserPromptExpansion)? · Check: read every sentence relying on the hook. · Fix: correct the claim or move the gate to an event that gives it.
- **HK-04** · MUST · Does a gating hook fail closed safely: (a) on the script's hook path, `set -E` with an ERR trap and a dependency check that exit 2 (Stop/SubagentStop: only after reading `stop_hook_active`), while a documented mode the hook command never passes (a `--flag` the main thread runs, such as `--direct`) may use other exit codes — a narrowing that holds for hooks LNT-34 does not judge (settings.json hooks); a POSIX sh hook registered in settings.json with `"onFailure": "block"` (POSIX sh has no `set -E`) meets (a) with an EXIT trap that prints a deny on any exit before a decision, in place of `set -E` and an ERR trap; (b) the skill's first step after enabling the hook confirms it ran (its stderr line or `/hooks`) before relying on it, and a timeout never counts as a block, unless the hook entry sets `"onFailure": "block"` and a step of the skill checks that the entry has it, so a crash or timeout blocks the call (Versions); (c) on a matcher-capable event, a narrow anchored matcher — on a matcher-less event, it blocks only after an in-script guard has matched — plus a documented disable path (env flag or settings removal); (d) do advisory hooks state that they fail open? · Check: report FAIL(a–d); LNT-34 flags exit codes other than 0 and 2. · Fix: add `set -E` and `trap 'echo "<hook>: internal error" >&2; exit 2' ERR`, the guard or anchor, and the disable note.
- **HK-05** · MUST · Does the hook block correctly — exit 2 or JSON deny (one style per hook), only on events that can block, with a reason giving what was detected, why, and the alternative? · Check: read the exit paths. · Fix: use exit 2 or `permissionDecision: deny` with `reason`.
- **HK-06** · MUST · Is output correct — (a) stdout only JSON built with `jq` (a fixed literal deny only when jq itself is missing, for hooks LNT-34 does not judge: settings.json hooks), fields at the right level, `updatedInput` complete, text the hook adds to the context (`additionalContext`, `systemMessage`, a reason) under 10,000 chars, on a channel Claude sees; the cap does not apply to `updatedInput`, which replaces the tool's input (Versions); (b) factual, not imperative, no untrusted text in `classifierContext`; (c) volatile values from SessionStart or a live read, never replayed stale on resume? · Check: report FAIL(a|b|c). · Fix: build with `jq -n`; nest under `hookSpecificOutput`; read volatile state live.
- **HK-07** · MUST · Do Stop/SubagentStop hooks read `stop_hook_active` before any dependency check and exit 0 when it is true (a Stop hook that must keep Claude going more than once in one turn may skip that exit only by stating its own bound: a per-state tries cap that always ends by letting the stop through, written in its `--help` and in a comment where the guard would sit), read `last_assistant_message` (or the `SubagentHandback` tool input), and do SubagentStop hooks match an agent type or no-op on an empty `agent_type`? · Check: read; no early exit and no such stated cap, or a cap whose last try still keeps Claude going, is FAIL. · Fix: move the guard to the top, or state the cap in `--help` and the comment and let the stop through after the last try; read the documented field; add the matcher.
- **HK-08** · MUST · Are event, type and matcher right — event by cadence, type supported by the event, command hooks for deterministic checks, `if` only on tool events and never as a security gate? · Check: judge beyond LNT-33 (schema and anchoring). · Fix: change event or type; use permission rules for hard gates.
- **HK-09** · SHOULD · Are hooks independent — no reliance on order, no two hooks rewriting the same input, no duplicate of a settings handler — with changing rules read from data files by one fixed dispatcher? · Check: read. · Context: `~/.claude/settings.json` and project `.claude/settings*.json` hooks. · Fix: merge duplicates; give one hook the rewrite.
- **HK-10** · MUST · Is the command robust — exec form or quoted placeholders, cwd-independent paths, an explicit timeout within the event's budget, validated input, path traversal and sensitive files blocked? · Check: read. · Fix: quote every variable; absolute paths; set `timeout`; reject `..`.
- **HK-11** · SHOULD · Was the hook tested by piping sample JSON, its registration confirmed (`/hooks`, `--debug`), and its regexes tested? · Check: read the test notes or script. · Fix: add a test that pipes fixtures and checks the exit code and JSON.
- **HK-12** · MUST · Does the hook never return `permissionDecision: "allow"` or an `updatedInput` that changes what a command does, unless the skill states that exact auto-approval and the matcher is anchored to it? · Check: LNT-34 flags both; judge the stated exception. · Fix: return deny, ask or `additionalContext` instead.
