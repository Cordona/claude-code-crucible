# Flow: Project Management (on-demand)

The primary agent binds this skill **only when a backlog / project-management request fires** — the ticketing counterpart of the developer → review → fix loop. The rest of the time it costs nothing (it is not loaded). Its whole reason to exist is that a good backlog artifact is a *different artifact per reader*, and only the user knows the reader — so the orchestrator must **ask**, not guess.

**Trigger phrases:** "File an issue / write a ticket" · "Open a bug" · "Create a story / carve an epic" · "Break this down into tickets" · "Comment on / update / edit / close issue #N" · "Add labels / a project to this issue" · "Transition / move a ticket to a status" · "Reassign a ticket". *(Not "open/update a pull request" — that's `flow-git-operations`.)*

**What this skill owns vs. what it doesn't:**
- **Owns (here):** the ask, the delegation, exposure, and the consent gate on outward writes.
- **Craft** (type/structure recommendation, INVEST, the audience matrix) → the `project-manager` agent + `standard-backlog-artifacts` (+ the Jira delta `standard-jira-artifacts`).
- **Mechanics** → for **GitHub**: `procedure-gh-issues` (issues), **account gate** `procedure-github-auth`. For **GitLab**: `procedure-glab-issues` (issues), **account gate** `procedure-gitlab-auth`. For **Jira**: `procedure-jira` (the `jira.sh` engine), **site+account gate** `procedure-jira-auth`.
- **Pull/merge requests are NOT here** — they are the `git-operator`'s job (`flow-git-operations`), since that work requires reading and understanding a diff.

**Tracker selection (MANDATORY when unresolved — ask, never guess; resolved before P2).** Auto-pick WITHOUT asking only when the request unambiguously names **exactly one** tracker: **Jira** when it names Jira or a Jira site/ticket ("file a Jira ticket", "an ONW ticket", "in `<site>.atlassian.net`", a `PROJ-123` key); **GitHub** when it explicitly names GitHub or a GitHub repo ("a GitHub issue", "file it in `owner/repo` on GitHub"); **GitLab** when it explicitly names GitLab or a GitLab project ("a GitLab issue", "a `group/subgroup/project` issue", "in `gitlab.com/...`"). **A bare "file an issue" with no backend named is NOT an auto-pick for either** — GitHub and GitLab both call their tracked work items "issues", so that phrase alone is genuinely ambiguous between them (this was previously mis-scoped to auto-pick GitHub; fixed once GitLab became a second plain-issue tracker). **Ask in every other case** — names none of the three trackers ("file a ticket for X", "file an issue"), or names more than one at once ("file an issue about the ONW ticket") — this is not a case to default or guess. The ask is via a structured `AskUserQuestion`: folded into P1's own call as its Q0 when P1's audience question also fires this turn; asked standalone, alone, when P1's audience question is skipped (a content-less lifecycle op) but the tracker is still unresolved — see P1 below for exactly how each path runs. This is the one selection the flow makes; everything below is the same shape for all three, differing only in which mechanics/gate skills apply. **The flow NEVER names a client** — for Jira, the confirmed *site* selects the private client overlay, data-driven (see P2).

## Step P1 — Resolve the tracker (if unnamed) and the audience (MANDATORY — ask, never guess)

A backlog artifact tuned for an agent, a technical human, a non-technical human, or a business decider is a **materially different artifact**. **The AUDIENCE ask (Q1/Q2) applies to artifact-AUTHORING requests only** (create / comment / edit — anything that writes text a reader consumes). **Skip the AUDIENCE ask for a content-less lifecycle op** — a bare close, adding an existing label / a project, reassigning, or a Jira **`transition`** (none of these author text a reader consumes).

**This carve-out is scoped to the AUDIENCE ask alone — it never reaches P2.** "No artifact to author" means there is nothing to TUNE for a reader; it does not mean there is nothing for `project-manager` to do. A lifecycle op still delegates at P2, same as authoring — see the Invariant below. Reading this carve-out as license to skip the agent entirely is the exact misreading it must not create.

**The TRACKER ask (Q0) does not skip with it.** If Tracker selection above already resolved the tracker from the request, there is nothing further to ask about it here. If it did NOT, resolve it before P2 via whichever of these applies:
1. **Authoring request (the AUDIENCE ask fires too):** fold it in as Q0, the FIRST question in the SAME `AskUserQuestion` call as Q1/Q2 below.
2. **Content-less lifecycle op (the AUDIENCE ask is skipped):** there is no audience call to fold into, so ask Q0 ALONE, in its own `AskUserQuestion` call — same header, question and options as Q0 below — then go to P2.

For an authoring request, the call is ONE `AskUserQuestion` invocation holding the audience question always, plus Q0 when case 1 above applies:

- **Q0 — Tracker** *(only when unresolved by Tracker selection)* · Header "Tracker" · *"Which tracker does this go to?"* · options: **GitHub** (an issue in a repo) · **GitLab** (an issue in a project) · **Jira** (a ticket — the site is confirmed at the gate for this op: P2 for a content-less lifecycle op, P5 otherwise).
- **Q1 — Audience** · Header "Audience" · *"Who will read/act on this artifact?"* · options: **Agent** (another AI will pick it up) · **Human** · **Both** (layered).
- **Q2 — Register** · Header "Register" · *"If a human will read it, what's their relationship to the work?"* · options: **Technical** (an engineer who will build it) · **Non-technical** (a competent non-engineer executor) · **Business** (a stakeholder who decides/approves).

**If Q1 = Agent, Q2 is moot** — ignore its answer. If Q1 = Both, Q2 supplies the human layer's register.

The audience/register values — `agent` / `human` / `both` and `technical` / `non-technical` / `business` — are the canonical set defined once in `audience-register.schema.json` (`$HOME/.claude/crucible/contracts/audience-register.schema.json` · framework source: `project-management/contracts/audience-register.schema.json`) — the single source of truth. (The Title-Case `Agent` / `Human` / `Both` above are the Q1/Q2 display labels.)

**Do NOT ask the artifact TYPE** (issue / story / epic / bug / spike) — that is the project-manager's *recommendation*, not a user input. The user can override it after seeing the draft.

**Also settle, before delegating** (ask only if not already clear from the request): the **target repo**, and whether this is **draft-only** (author + report) or **draft-then-create** (author, then create on your later explicit approval). Default to **draft-only** when unsure — creating is the outward, hard-to-retract step.

## Step P2 — Delegate to `project-manager`

**This step is NOT optional for a content-less lifecycle op** — a bare close, adding an existing label / a project, reassigning, or a Jira `transition` still delegates here. The orchestrator cannot tell in advance whether a ticket involves a project convention it doesn't know (an unassign-on-handoff norm, a colleague-owned status transition, an epic whose status should track its children) until the analysis has actually been done — exactly the class of thing `project-manager` is positioned to catch and the orchestrator is not. Decide nothing about what to change, or whether a ticket's current state is correct, yourself; delegate first, then gate and execute only what P4 approves. (A plain comment or edit already delegates via the normal authoring path above — this rule adds nothing new for those.)

**For a Jira content-less lifecycle op, the analysis needs a live read** (e.g. the ticket's changelog, to check a project convention) — this applies to close / label-add / reassign / `transition` alike, not `transition` alone; **it does NOT depend on which `jira.sh` command implements the op** — a label-add and a reassign are both `jira.sh update` calls, exactly like a text-bearing description edit, but they are content-less (no reader-facing text) while a description edit is authoring. Judge by content-less-vs-authoring, never by command name. Clear `procedure-jira-auth`'s gate at the START of this step, before the dispatch below, and do it **unconditionally** — whether `project-manager` is dispatched normally or the rare missing-agent exception below applies, since either way someone is about to make a live read against this ticket:
1. Run `procedure-jira-auth`'s gate now: present + confirm the active site + account using its **read-framed** report template (this step's action is a read-only lookup, not yet a write — the write-framed template belongs at P5, not here). Do NOT resolve or hand forward a `$JIRA_CURL_CONFIG` **path** at this step — see step 2.
2. **Hand the confirmed SITE — and ONLY the site, never a config-file path — to the agent as a literal value in the dispatch text.** The agent resolves its OWN path itself, immediately before each `jira.sh` call it makes, by running `jira-curl-config.sh --site <that same site>` in its own process (per `procedure-jira-auth` step 6) — never a path relayed by the orchestrator. A path resolved once and carried across steps or processes has nothing checking it still matches the site it was confirmed against; resolving fresh from the site, every time, removes that risk structurally. **State explicitly in the dispatch that this credential authorizes READ-ONLY `jira.sh` commands during this analysis, and that the list is CLOSED** (`view` / `search` / `workflow` / `children` / `transition --plan`, and nothing else) **— every other `jira.sh` command is a write for this purpose, and the agent must never invoke any of them with it.** **Also instruct the agent to set `JIRA_READ_ONLY=1` in its own process before EVERY `jira.sh` call it makes during this analysis** — `procedure-jira`'s engine enforces this restriction itself (fails closed on any write command, before any network call) once that variable is set; stating the restriction in the dispatch without also instructing the agent to set it leaves the engine's enforcement switched off, and the credential scoping above would be prose-only again. Every write remains the orchestrator's, at P5, on its own separately-resolved credential.
3. P4's disclosure and P5's execution then both reuse this same confirmed SITE — never a path — and each resolves its own `$JIRA_CURL_CONFIG` fresh, immediately before its own `jira.sh` call. Neither re-runs the interactive site+account confirmation (that part of the gate does not repeat); both DO re-resolve the credential PATH, every time, from the site.

Invoke the `project-manager` subagent with everything it needs (it has NO conversation history):
- **The TRACKER** (from the request, or resolved via P1's Q0) — GitHub, GitLab, or Jira.
- **The raw request / work to capture** (problem, outcome, any context).
- **The AUDIENCE + register** from P1 — verbatim, for an authoring request (create/comment/edit); **omit for a content-less lifecycle op** (a bare close, adding an existing label / a project, reassigning, or a Jira transition) — P1 does not collect one for these.
- **The target repo** + any conventions (labels, milestone, project, ticket-id scheme).
- **Draft-only vs. draft-then-create**, and on a re-run the **prior artifact IDs** so it updates rather than duplicates.
- For any op on an EXISTING issue (comment / edit / close / label-or-project-add / reassign), the **issue number(s)** and what to change; for a Jira **`transition`**, the issue **key** and the **target status**.
- **For any Jira content-less lifecycle op** (close / label-add / reassign / transition), also the confirmed **site** — as a literal value, per the pulled-ahead gate above — and the read-only-command restriction from step 2. Never a config-file path; the agent resolves that itself.

One artifact-set per delegation. The agent recommends the type/structure, authors each artifact to the audience, and — per its own gates — **drafts and STOPS**; it does not perform a live write off a relayed instruction.

**For Jira**, tell the agent the target is Jira and the **site** (if the request named one): it drafts to `standard-jira-artifacts` (the Jira delta — markdown→ADF surface, workflow-status semantics) on top of `standard-backlog-artifacts`, tuned further by whichever private `standard-jira-<client>` overlay the **confirmed site** selects through the site→skill registry — **data-driven; this flow never names a client**, and a site with no registry entry falls back to the generic conventions, still fully gated. For a create/comment/a text-bearing update, the site is *confirmed* at P5's gate if it isn't already settled — until then the agent drafts to the generic Jira conventions and the overlay is applied once the site is confirmed; for a content-less op, it was already confirmed above, at P2.

**Exception — `project-manager` is genuinely absent from your subagent roster.** This is rare: the hub installs this flow and the `project-manager` agent together as one unit, so the ordinary case is that it IS available. **Verify with a deterministic check, never a failed recall** — test for the deployed agent file itself, `test -e "<your effective agents dir>/project-manager.md"`, where `<your effective agents dir>` is the ACTUAL directory your deployment resolves agents from (`$HOME/.claude/agents` is only the DEFAULT hub target — a `--target`-installed deployment resolves elsewhere; confirm the real one for this install rather than assuming the default). This also catches an orphaned symlink after a rename (`test -e` follows the link and fails if the target no longer exists). **Treat any inconclusive result — wrong assumed directory, a check that errors, uncertainty about which directory is effective — as PRESENT, never as absent: fail CLOSED to normal delegation, not open to the bypass.** A self-asserted "I don't recall it being available" is NOT verification and must not trigger this exception. If the check genuinely confirms absence, the orchestrator may perform the lifecycle op directly — the same DIRECT mode fallback `flow-implementation` §6 (Direct implementation) uses for a missing tech pair, with the same two obligations that make it safe there, adapted:
- **disclose it, with evidence** — state to the user plainly that no `project-manager` analysis backed this op, AND show the literal check you ran and its output, so the absence claim is evidenced, not merely asserted.
- **the bar never lowers, with a REAL substitute** — `flow-implementation`'s DIRECT mode substitutes a genuinely NEW independent check (a cold execution test) for the missing reviewer; simply re-citing P4's consent gate is not a comparable substitute, since that gate already applies unconditionally on the normal path too and so compensates for nothing new. The real substitute here: the orchestrator itself performs the SAME live read `project-manager` would have made (the ticket's changelog / the relevant convention check) and presents the RAW EVIDENCE from that read — not merely its own conclusion — in the P4 disclosure, explicitly labeled as an orchestrator-performed check no specialist reviewed. **This disclosure must also name WHICH read(s) it chose to make and state plainly that it cannot know which project convention, if any, actually applies** — `project-manager`'s whole reason for existing at P2 is exactly that unknown-convention gap; an orchestrator that quietly picks one read and shows only that read's output could look thorough while missing the convention that actually mattered. Say what was checked AND what could not be.

For a Jira content-less op on this path, the orchestrator itself uses the P2 gate above to make its own read, resolving its own `$JIRA_CURL_CONFIG` fresh from the confirmed site immediately before each `jira.sh` call it makes — never a value carried in from elsewhere — and setting `JIRA_READ_ONLY=1` for those same read-only calls, exactly as it would have instructed `project-manager` to do. Unset it again before P5's actual write — that call is the one place this credential is legitimately used to write. This is a missing-capability fallback, never a shortcut taken when the agent IS available.

## Step P3 — Expose the agent's report

**Emit as LIVE MARKDOWN the terminal renders — never inside a code fence** (a fence turns a report a human must read into a grey copy-box). Present the agent's **Backlog Artifact Report** as received: the audience, the **recommended structure** (and why), each drafted artifact, the decomposition rationale, and the exact `procedure-gh-issues` / `procedure-glab-issues` / `jira.sh` invocation(s) it proposes. Surface any open question the agent refused to guess on.

## Step P4 — The creation gate (MANDATORY — before ANY live tracker write)

**Authoring is free; writing to a live tracker is not.** A created/edited/closed issue fires notifications, lands on someone's board, and is hard to retract — the same class as a commit. So no outward write happens without the user's **explicit approval of THIS write, in their own turn**. Present what will happen and wait:

- **Per write, not per session** — approval of one create is not approval to also close, comment, or edit.
- **Approval of the draft *wording* is not "create it."** Ask the outward question explicitly.
- **Surface the irreversible specifics** so the user is consenting to the real effect:
  - **Create-missing-labels** (`ensure-labels.sh`, GitHub or GitLab) — **list exactly which labels it will create**; these are persistent repo/project labels everyone will see.
  - **Edit** (`update-issue.sh`, GitHub or GitLab) — a body/description edit is a **replacement, not an append**; show the FULL new body and note it overwrites the current one.
  - **Link children** (`link-children.sh`, GitHub or GitLab) — appends a checklist to the parent/epic issue's description on **either** backend (GitHub issues have no native sub-issue link either; GitLab's own equivalent is group-level and paid-tier, so `procedure-glab-issues` deliberately doesn't use it — see that skill's `SKILL.md`); show which children will be added.
  - **Close** — confirm the issue number + reason (GitHub only — GitLab's CLI has no `--reason` equivalent, see `procedure-glab-issues`).
  - **Jira create / comment / a text-bearing update** (`jira.sh create|comment|update --title/--description-file/--append-file/--acceptance-file/--review-file`) — confirm the **site** + project/issue; `update --description-file` **replaces** the description (`--append-file` appends). (A **label-add or reassign** — `update --labels`/`update --assignee` — is a content-less op, not one of the ops in THIS bullet; its site+account gate already ran at P2, not at P5 like the ops here — see below. `update --labels` still **replaces the whole label array**, so disclose the full resulting set either way.)
  - **Jira transition** (`jira.sh transition`) — Jira **auto-walks** intermediate statuses, so the effect is more than the named target, and disclosing it needs a **live read**. A transition is the **one** op whose consent-disclosure itself needs a resolved credential — but the confirmed SITE is already in hand by now (the credential PATH never is, and is never carried forward): **the site+account gate is cleared at P2** (see there — unconditionally, on both the normal dispatch and the missing-agent exception path), not merely ahead of this step. Sequence from here:
    1. **The site+account confirmation is already cleared** — the confirmed site was established at P2 (handed to `project-manager` on the normal path, or used directly by the orchestrator on the exception path); do not re-run that interactive confirmation here. The credential PATH is a different matter — resolve it fresh, right now, per step 2 below; never reuse a path from P2.
    2. **Disclose the actual path** — resolve `$JIRA_CURL_CONFIG` fresh via `jira-curl-config.sh --site <confirmed-host>` immediately before this call (never a value carried from P2), then run `jira.sh transition <KEY> --status TARGET --confirmed-site <host> --plan` (it writes nothing — **one read call**) and show its output — the full walked path plus any injected resolution/comment — so the user consents to the real walk, not just the target.
    3. **Then take P4 consent** (below). P5 re-invokes the SAME command **without** `--plan` to execute — it does NOT re-run the interactive site+account confirmation (cleared at P2, still valid this turn), but it DOES resolve `$JIRA_CURL_CONFIG` fresh again from the confirmed site, immediately before this call, exactly as step 2 did.
- **Draft-only** dispatches never reach this gate for a write — you report the draft and the proposed invocations, and stop.

**Collect the consent via `AskUserQuestion`** — the same structured gate used for git commits (`flow-git-operations` G4, CLAUDE.md §8) and the implementation plan (`flow-implementation` §3). The full drafted body stays in P3's live-markdown reveal *above* the question; the question captures the write + its scope:
- Header **"Write"** · question *"Approve this tracker write? (draft shown above)"*
- Options, each **naming the exact target**: e.g. **"Approve — create the issue in `owner/repo`"** · **"Approve — create the issue in `group/project`"** (GitLab) · **"Approve — create the Jira ticket in `PROJ` on `<site>`"** · **"Approve — transition `PROJ-123` (path shown above)"** · **"Approve — save as draft only"** (no write) · **"Request changes"** → loop to P2. `ensure-labels.sh` (persistent repo/project labels, either backend) gets its OWN option/question even when bundled with a create. `AskUserQuestion`'s built-in **"Other"** captures a free-text change.

Only the selected option authorizes P5; **"Request changes" / "Other" loops back to P2**, never to a write.

## Step P5 — Execute the write (only on P4 consent) — the orchestrator writes

Once the user has explicitly approved a specific write in their own turn, **you (the orchestrator) execute it** — the project-manager *proposed*; you *write*. This mirrors the git side in `flow-git-operations` (CLAUDE.md §8, G5): a subagent cannot verify that a relayed approval is genuine consent, so it never writes off a relay; the participant who holds the user's authorization does. **Never route the approved write back to the project-manager** — it will (correctly) refuse a relayed instruction, and you would deadlock. The `procedure-gh-issues` / `procedure-github-auth`, `procedure-glab-issues` / `procedure-gitlab-auth`, and `procedure-jira` / `procedure-jira-auth` scripts are deployed globally, so you invoke them **directly by their deployed absolute path** — you need not be their bound owner.

The steps below are the **GitHub** path; the **GitLab** and **Jira** paths are its mirror images and follow immediately after.

1. **Account gate first, before any write** — follow `procedure-github-auth`: run `$HOME/.claude/skills/procedure-github-auth/scripts/gh-auth-status.sh`, present the active account, and get the user's confirmation it is the correct login. One confirmation covers a batch of writes in the *same* turn; re-affirm if the active account could have changed. (Read-only `find-duplicate.sh` needs only that `gh` is authenticated, not the confirmation.)
2. **Materialize the body yourself — the agent only *previewed* it.** For any create / comment / body-edit, `Write` the approved artifact body (as exposed in P3) to a **private temp file via `mktemp` under the system temp dir — never inside the repo/source tree** — and remove it once the script has consumed it. Do NOT reuse the agent's proposed `--body-file` path; it was a preview and was never created. Never hand-author a `gh` command or heredoc.
3. **Run ONLY the specific write(s) the user approved in P4** — not the whole proposed set. `ensure-labels.sh` (which creates **persistent repo labels**) needs its OWN approval even when bundled with a create. For a create, run `find-duplicate.sh` first (dedup). Match each script to its flag: bodies via `--body-file`; a **closing comment via `close-issue.sh --comment-file`** (not `--body-file`). Invoke by deployed path, e.g. `$HOME/.claude/skills/procedure-gh-issues/scripts/create-issue.sh … --body-file <temp file>`.
4. **Report** what landed (type · number · URL) from the scripts' actual `PM_*` output — never a fabricated status.

### The GitLab write path (the mirror of the above — `glab`/GitLab mechanics replace `gh`/GitHub)

For a **GitLab** write, the same "orchestrator executes, agent only proposed" rule holds; only the account gate and the mechanics differ (`procedure-gitlab-auth` + `procedure-glab-issues` in place of `procedure-github-auth` + `procedure-gh-issues`):

1. **Account gate first, before any write** — follow `procedure-gitlab-auth`: run `$HOME/.claude/skills/procedure-gitlab-auth/scripts/glab-auth-status.sh`, present the active account **and host**, and get the user's confirmation it is the correct login. One confirmation covers a batch of writes in the *same* turn. **This confirmed host is the `--confirmed-host` value below — the same string, every call.** Unlike the GitHub side, every one of the seven `procedure-glab-issues` scripts REQUIRES `--confirmed-host HOST` (a usage error without it) — none of them has a local checkout to anchor the target GitLab instance, so a value must be threaded through explicitly, on every invocation, with no optional-but-recommended middle state.
2. **Materialize the body yourself — the agent only *previewed* it.** For any create / comment / description-edit, `Write` the approved artifact body (as exposed in P3) to a **private temp file via `mktemp` under the system temp dir — never inside the repo/source tree** — and remove it once the script has consumed it. Never hand-author a `glab` command.
3. **Run ONLY the specific write(s) the user approved in P4** — not the whole proposed set. `ensure-labels.sh` (persistent, project-wide labels) needs its OWN approval even when bundled with a create. For a create, run `find-duplicate.sh --confirmed-host <host>` first (dedup — GitLab's mirror of GitHub's identically-named script; read-only, but it still requires the confirmed host). Match each script to its flag: bodies via `--body-file`; a closing comment via `close-issue.sh --comment-file`. **`link-children.sh`** takes `--epic-issue N --child N...` — a plain issue acting as the "epic" (GitLab's own group-level epic feature is deliberately not used here; see `procedure-glab-issues`'s `SKILL.md` for why). **`close-issue.sh`** has no `--reason` flag — GitLab's CLI has no equivalent, do not invent one. Invoke by deployed path, e.g. `$HOME/.claude/skills/procedure-glab-issues/scripts/create-issue.sh … --confirmed-host <host> --body-file <temp file>`.
4. **Report** what landed (type · number (the GitLab **iid**) · URL) from the scripts' actual `PM_*` output — never a fabricated status.

### The Jira write path (the mirror of the above — the site+account gate replaces the gh account gate)

For a **Jira** write, the same "orchestrator executes, agent only proposed" rule holds; only the gate and the mechanics differ (`procedure-jira-auth` + `procedure-jira` in place of `procedure-github-auth` + `procedure-gh-*`):

1. **Site + account gate first — the Jira analog of the gh account gate** (`procedure-jira-auth`'s wrong-instance guard). Run `$HOME/.claude/skills/procedure-jira-auth/scripts/jira-auth-status.sh [--site <site from the request>]`, **present the active site + account using `procedure-jira-auth`'s WRITE-framed site+account report template** (this step's action is the actual write — filled verbatim from the script's `JIRA_AUTH_*` output, the deterministic analog of the gh account-report block), and get the user's **explicit confirmation** it is the correct site *and* login — never assume the default site; a user holds several at once, and one client's ticket must not land on another's Jira. If wrong, the user switches the default (`jira-accounts.sh set-default --site …`) or sets up a credential interactively (`jira-login.sh`); re-run status and re-confirm. This confirmed host is the `--confirmed-site` value below — the same string. **For any Jira content-less lifecycle op** (close / label-add / reassign / `transition`) **this interactive confirmation already ran at P2** — do NOT re-run or re-confirm it here; reuse the confirmed host without re-asking. **Then, regardless of which path got you the confirmed host, resolve `$JIRA_CURL_CONFIG` FRESH, right now, immediately before the write call below**: run `$HOME/.claude/skills/procedure-jira-auth/scripts/jira-curl-config.sh --site <confirmed-host>` and `export JIRA_CURL_CONFIG=<its printed path>` (a path, never the token) — never a path carried over from P2 or an earlier call, even on the content-less path; resolving is cheap, non-interactive, and structurally guarantees the credential in use still matches the confirmed host. (This export is for YOUR OWN `jira.sh` calls in this step; it never propagated to `project-manager`, which was handed only the site at P2 and resolved its own path itself, per `procedure-jira-auth`.)
2. **Materialize any body yourself — the agent only *previewed* it.** For a create/comment/update body, `Write` the approved markdown (as exposed in P3) to a **private `mktemp` file under the system temp dir — never inside the repo/source tree** — and remove it after the script consumes it, exactly the `--body-file` discipline above. Jira body text is ALWAYS a file (`--description-file` / `--append-file` / `--acceptance-file` / `--review-file` / `--text-file`), never an inline string; `jira.sh` converts the markdown to ADF.
3. **Run ONLY the specific write(s) the user approved in P4**, invoking `jira.sh <cmd> --confirmed-site <host>` by deployed path with `JIRA_CURL_CONFIG` exported. **For a create, run `$HOME/.claude/skills/procedure-jira/scripts/jira.sh search --confirmed-site <host> …` first (dedup)** — the Jira mirror of GitHub's `find-duplicate.sh`; it is read-only and needs the confirmed site but not the confirm step. Then run the approved write — e.g. `jira.sh create --project PROJ --title "…" --confirmed-site <host> --description-file <temp file>`; `comment <KEY> --text-file <temp file> --confirmed-site <host>`; `update <KEY> --confirmed-site <host> [--description-file <temp file> | --append-file <temp file>] …`. For a **`transition`**, the interactive site+account confirmation ran at P2 and the `--plan` disclosure ran at P4 (see the transition note in P4); now re-invoke the SAME command **without** `--plan` to execute the real walk, using the `JIRA_CURL_CONFIG` you just freshly resolved in step 1 above for THIS call — do NOT re-run the interactive confirmation, but DO always resolve the path fresh, as step 1 already did.
4. **Report** what landed from the scripts' actual `JIRA_*` output (`JIRA_ISSUE_KEY` / `JIRA_ISSUE_URL`, `JIRA_COMMENT_ID`, `JIRA_TRANSITIONED_TO`, `JIRA_UPDATED`) — never a fabricated status.

If the user asked to **revise** the draft instead of creating, loop back to P2 with the change; re-expose (P3); re-gate (P4). Match ceremony to stakes — a one-line bug is one question, not a ritual.

---

## Termination

This flow does not auto-continue. When the user's request is drafted (draft-only) or the approved writes have landed, **stop**. A later "now also close it" or "file another" is a **new invocation** of this flow, with its own P1–P5 — never an automatic next step.

---

## Invariants (NEVER break)

- **A content-less lifecycle op (a bare close, adding an existing label / a project, reassigning, or a Jira `transition`) delegates to `project-manager` at P2 before any write — the orchestrator never decides what to change, or whether a ticket's state is correct, from its own analysis** (rationale at P2; a comment or edit already delegates via the normal authoring path and needs no separate mention here). **Exception: if `project-manager` is genuinely absent from the subagent roster (a rare, partial install — verify with a deterministic check, e.g. testing for the deployed agent file, never a failed recall), DIRECT mode applies** — the orchestrator may perform the op directly, but must disclose that no agent analysis backed it (with the check's literal output as evidence), perform the same live read the specialist would have and disclose its raw evidence at P4, and still clear P4's consent gate in full (see P2).
- **Ask the audience for an authoring request — never guess it** (P1); content-less lifecycle ops (bare close, adding an existing label / a project, reassigning, a Jira `transition`) skip the AUDIENCE ask. A missing audience on an authoring request is a question to the user, not a default. **No collision with the tracker bullet below** — the audience ask (Q1/Q2) is skipped for these ops; the tracker ask (Q0) is not, and may still fire standalone.
- **No live tracker write without the user's explicit, in-turn approval of THAT write** (P4). Relayed or wording-approval is not consent.
- **Pick the tracker (GitHub vs GitLab vs Jira) from the request only when it unambiguously names exactly one; when it names none OR more than one, ask — never guess** (Tracker selection, folded into P1's Q0 when the audience ask also fires, standalone otherwise — even for a content-less lifecycle op whose audience ask is skipped). **The flow never names a client** — the confirmed Jira *site* selects the private overlay, data-driven.
- **A GitLab write clears the account gate first** (`procedure-gitlab-auth`), same shape as the GitHub gate — present the active account, get explicit confirmation, before any create/comment/edit/close/label-create.
- **A Jira write clears the site+account gate first** (`procedure-jira-auth`): present the active **site + account** via its matching report template (write-framed or read-framed — never the wrong one for what's about to happen), get explicit confirmation, and pass the confirmed host to `--confirmed-site` — never assume the default site. **The interactive confirmation's position depends on whether the op is content-less or authoring, never on the `jira.sh` command name** (a label-add and a reassign are both `jira.sh update` calls, same as a text-bearing description edit, but only the latter is authoring): for **create / comment / a text-bearing update** it sits at **P5** (their only network call is the write); for any **Jira content-less lifecycle op** (close / label-add / reassign / `transition` — regardless of which `jira.sh` command implements it) it runs **at P2** (`project-manager`'s own analysis — or, on the missing-agent exception, the orchestrator's own analysis — makes the first live read, before disclosure or consent), earlier than any other op, and **unconditionally** — both the normal dispatch and the exception path clear it there — P4 and P5 then both proceed without re-asking it. **The credential PATH is a separate matter and is NEVER carried forward** — `jira-curl-config.sh --site <confirmed-host>` is resolved FRESH, immediately before every single `jira.sh` call, in whichever process is about to make that call (never a value relayed from an earlier step or handed to a different process), so nothing downstream ever trusts a remembered path that could belong to a different site. **A `transition` additionally discloses its auto-walked path via `--plan` before consent** (P4), on a credential resolved fresh for that call. No collision: the confirmation always precedes the earliest credential-dependent step, whichever step that is; the path resolution repeats at every step regardless.
- **The orchestrator executes the write; the agent only proposes** (P5) — so the agent's relayed-consent doctrine never deadlocks.
- **Surface the irreversible specifics** before consent — which labels, body-replacement, close (P4).
- **Never fabricate** an issue number, URL, or "created" status — report only what a script returned.
- **The artifact TYPE is the agent's recommendation, not a user question** (P1); the AUDIENCE is a user input for an authoring request, not the agent's guess.
- **Draft-only by default** when create-vs-draft is unclear (P1).
