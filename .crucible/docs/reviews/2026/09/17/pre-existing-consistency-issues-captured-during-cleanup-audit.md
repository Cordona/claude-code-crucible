# Pre-Existing Consistency Issues — Captured During the Cleanup-Integrity Audit

**Date:** 2026-09-17
**Status:** CAPTURED, not fixed. Deliberately deferred to a separate future pass.

**Context:** a different session ran a large changelog/version-stamp/dev-process-narration cleanup across 60 files on `chore/framework-improvements` (uncommitted). This session ran an independent audit of that cleanup in five passes: (1) per-file "was anything essential removed" check, (2) an adversarial second-opinion pass on the same question, (3) an internal self-contradiction check + a cross-reference accuracy check against a mechanically pre-resolved reference map, (4) a reverse cross-reference check (do files outside the 60 cite something in the 60 that's now stale), (5) an execution test — actually simulating following the highest-stakes edited flows step by step against concrete scenarios, rather than comparing text statically. Passes 1–2 found and fixed one real regression (`procedure-git-identity`, a deleted sentence describing real control-character/pattern-injection hardening in `resolve-identity.sh`). Pass 3 found 18 more flagged tensions; pass 5 found 9 more, of a different kind (procedural gaps only visible by simulation, not text comparison). Every one of these 27 was individually verified against `git diff HEAD` (and, for cross-reference/execution-test findings, the actual cited target file) to determine whether the cleanup caused it. Pass 4 found 0 issues.

**2 of the 27 were genuinely caused by the cleanup** (a version-footer deletion removed the only sentence reconciling an internal tension elsewhere in the same file) — these were fixed in this session: `standard-clean-code` (test-file review scope) and `standard-react` (§9's security content vs. the file's own "no security content" scope disclaimer).

**The other 25 are captured below** (16 from pass 3, 9 from pass 5). Every one was verified, via `git diff HEAD` on the cited file(s), to be untouched by this cleanup — they predate it and are not this cleanup's fault. Some look like genuine defects worth fixing eventually; a few are lower-confidence and may turn out to be intentional framework idiom on closer reading. None were fixed here — this file exists so they aren't lost, not to adjudicate them.

## Self-contradiction findings (12 files/issues)

1. **`software-development/agents/specialists/git-operator/skills/procedure-gh-pr/skill/SKILL.md`** — the frontmatter/opening line describes the `git-operator` itself as running/talking to `gh` to open and edit PRs, while the file's own "gates the CALLER (the orchestrator — git-operator only plans) must clear" section says the git-operator only plans and the orchestrator executes the write. **Low confidence this is a real defect** — this loose-vs-precise phrasing pattern ("the procedure X runs" as shorthand for "X's toolkit") repeats across this framework's `procedure-*` skills and appears to be established idiom, not a contradiction; worth a second look before treating as a defect.

2. **`README.md`** — states the nine `lens-*` reviewers (including `lens-test-quality-reviewer`) "run **only** when a human asks for a review pass," but the same document's own "How a request flows" / Entry-modes-table description of `flow-testing` has `lens-test-quality-reviewer` run mandatorily once implementation is confirmed, with no review-pass request needed. Real gap in README's precision — CLAUDE.md itself distinguishes a "discretionary lens seat" from a flow's own "fixed seat," and README's phrasing doesn't carve that out.

3. **`project-management/flows/flow-project-management/SKILL.md`** — P5 step 3 says "for a `transition` or a `comment-edit`, the interactive site+account confirmation ran at P2/earlier," grouping `comment-edit` with the content-less ops that gate at P2. The Invariants section instead groups `comment-edit` with `create`/`comment`/a text-bearing `update` as ops whose confirmation "sits at P5." These directly disagree on where `comment-edit`'s confirmation actually happens. Confirmed via direct read of both passages in the current file — this is real, not a misread.

4. **`software-development/agents/specialists/git-operator/skills/standard-git-tag/SKILL.md`** — the "Release automation (optional)" section recommends **semantic-release** as a valid "zero-gate... fully automatic on merge, including publish" choice, while the Constraints section makes it an absolute NEVER to cut/publish a release tag without explicit, in-conversation authorization of that specific version/SHA. Worth checking whether the automation section needs a caveat that it's an alternative *policy* the human adopts up front (not a per-tag bypass) — as written, they read as flatly incompatible.

5. **`software-development/agents/specialists/git-operator/skills/procedure-git-ops/SKILL.md`** — the frontmatter/opening now says "the git-operator plans and the orchestrator executes... the git-operator itself runs only the read-only `preflight.sh`," while a later heading says "the gates the CALLER (the orchestrator — git-operator only plans) must clear." **Low confidence this is a real defect** — the "only plans" phrasing sits under a heading explicitly scoped to write-gates, so it likely means "only plans, with respect to writes," consistent with the preflight.sh carve-out stated elsewhere. Minor, probably not worth fixing.

6. **`CLAUDE.md`** (the live global config, not one of the 60 changed files — a pre-existing property of the operating document itself) — §1 "Primary Role: Orchestrator" says the orchestrator "delegate[s] review to a swarm of reviewers," while the same document's "Flow at a Glance (Mode IMPLEMENT)" section says "There is no swarm in this flow — dev-alone-first... or dev+reviewer together... never a lens," reinforced by the Invariants ("Lenses, panels, and tests never fire automatically"). The opening line is a loose gloss immediately superseded by the detailed section, so it doesn't change behavior, but it's sloppy and worth a wording pass.

7. **`software-development/flows/flow-decision/SKILL.md`** — two issues in one file: (a) the entry paragraph says "a panel spawns 3–4 Opus lawyers + an arbiter," but the rest of the document consistently states trio=2 lawyers/quartet=3 lawyers with a hard "3 is the ceiling, never a 4th" rule — "3–4 lawyers" doesn't match either figure under any reading. (b) §3d says the arbiter's mandate includes confidence as one of **three** standing duties, while §2 step 4's acceptance check treats "the two standing-duty lines" and "the Confidence line" as three separate required items without calling confidence a standing duty — arguably reconcilable as the same three things worded two ways, but worth tightening.

8. **`software-development/flows/flow-git-operations/SKILL.md`** — the Merge-Request Path's step 1 (planning) says the `--confirmed-host` it uses "is the one `procedure-gitlab-auth` already confirmed; see step 4's account gate for where that comes from," while step 4 (execute) runs strictly after step 1 in the same procedure and itself frames running the account gate as its own first action. **Low-to-moderate confidence** — plausibly just a forward-reference ("see step 4 for how this gets confirmed"), not a literal claim that confirmation already happened. Worth a wording check either way.

9. **`software-development/shared/standards/lens/standard-observability/SKILL.md`** — "Log an exception once, at the right level, with context..., then propagate or handle" sits immediately after "Log-or-throw, never both — `log(e); throw e;` double-reports up the layers... No silent swallow." The second bullet's "log... then propagate" reads as exactly the log-then-throw pattern the first bullet just forbade. Real, adjacent, worth reconciling (likely the second bullet means "at the one layer that legitimately terminates handling," but that's not stated).

10. **`software-development/flows/flow-spec/SKILL.md`** — the intro's "why this exists" paragraph says a large/ambiguous spec-worthy case should be **proposed** to the human, not decided alone, while §0 "Bind this skill when" lists "a single-repo interface decision is genuinely forked... and costly to get wrong" as a flat trigger with no propose-first caveat (unlike the neighboring multi-repo bullets, which do state a mandatory ask). Since judging an interface "forked and costly" is itself a self-judged call, this is a real procedural ambiguity about whether to propose or bind directly.

11. **`software-development/shared/review-report-standards/SKILL.md`** — the stated universal one-line finding template is `Status · file:line — problem → fix`, but the worked "Resolved this round" example leads with the reviewer's name ("**Kotlin Reviewer** · `order/place.rs:30` — ...") instead of the status word, with no stated carve-out for the Resolved/Acknowledged groups. Likely a stale worked example, low severity.

12. **`software-development/shared/standards/tech/standard-python/SKILL.md`** — the Concurrency & Parallelism bullet opens by saying threading doesn't (and can even slow down) CPU-bound work because of the GIL, then closes by recommending `asyncio.to_thread` "for genuinely CPU-bound work" alongside `multiprocessing` — but `to_thread` offloads to a GIL-bound worker thread, the same mechanism the bullet just called ineffective for that case. This looks like a genuine technical inaccuracy, not just a wording issue.

## Execution-test findings (9 issues, 4 files/groups) — found by simulation, not static analysis

**Added 2026-09-17, same day, before commit.** Before committing, this session ran three more checks: (a) a reverse cross-reference pass (do files OUTSIDE the 60 changed ones cite something in the 60 that's now stale — 38 citing files checked, 0 issues), (b) an independent sanity-check of the 2 fixes above (both confirmed accurate), and (c) an **execution test**: actually simulating following the highest-stakes edited flows step-by-step against concrete scenarios, rather than comparing text statically. All 4 groups tested came back with real findings — genuine procedural gaps that a static diff/contradiction check structurally cannot see, because they're about what happens when you reach a fork the text never resolves, not about two sentences disagreeing. Every one below was checked against `git diff HEAD` on its file and confirmed untouched by this cleanup (the diffs for all 4 files/groups only ever touched footer/narration text, never the loop logic, gate templates, or decision forks these findings cite) — pre-existing, not cleanup-caused.

17. **`CLAUDE.md`** — walking "commit that" right after a build finished with no reviewer run yet: the commit gate correctly identifies the correctness floor is NOT closed, but the text never states what happens next (refuse outright? auto-run the deferred reviewer? ask the human to choose?) — it only describes the information-gathering question, not the consequence of a known-negative answer.

18. **`software-development/flows/flow-implementation/SKILL.md`** — two gaps: (a) §5's fix-loop round 3 ("ONLY if a CRITICAL/HIGH is still open... stop regardless") has no action label, unlike rounds 1 ("FIX")/2 ("VERIFY") — unclear whether round 3 is a fix, a re-verify, or both, and the "stop regardless" phrasing means a security-critical finding could end the loop on the developer's own unverified fix claim. (b) §4c's "when flow-testing completes, resume here at §4d" never defines what "completes" means when flow-testing itself ends in an ESCALATION (its own bounded loop can do this) rather than a clean approval.

19. **`software-development/flows/flow-git-operations/SKILL.md`** — four gaps: (a) G1's per-class correctness-floor check ("if git-operator's split separates classes, check each commit's own class") is only possible after G2 produces the split, but G1 is headed "confirm ALL THREE before anything" (before G2 ever runs) — no step re-invokes this check once the split exists. (b) G1's worked human question is binary (proceed / finish the missing floor first) with no branch for a mixed answer on a mixed-class diff. (c) The Pull-Request Path's step-3 gate template still offers "open the PR" as an option even when step 1 already found an existing open PR for that head, which `create-pr.sh` will hard-fail on — no defined recovery if the human picks the doomed option. (d) There's no dedicated "Tag Path" the way there's a PR/MR path — a tag-only request (no accompanying commit) has to run through the commit-shaped G1-G5 procedure, whose G4 gate template literally asks "approve the commit(s) above?" with zero commits to point at.

20. **`software-development/flows/flow-review/SKILL.md`** — two gaps: (a) the frontmatter description states the Validate-First rule as an unconditional block ("bind only after the deferred reviewer pass has closed"), while the body (§0/§3) discloses a real escape hatch ("seat the {tech}-reviewer here explicitly") that the frontmatter never mentions — a reader going by the description alone gets a flat refusal with no alternative. (b) That same escape hatch collides with §5a's dispatch mechanism: seating the {tech}-reviewer "here" puts it in the same parallel batch as the quality lenses, with no staging to let its correctness pass finish first — exactly the "reviewing before correctness is confirmed" state §3 says this procedure exists to avoid.
