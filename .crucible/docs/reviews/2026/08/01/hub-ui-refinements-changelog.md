# Hub UI Refinements — Implementation Changelog

**Status:** in progress, direct implementation (no subagents installed at time of writing — framework was uninstalled for the migration; no self-review performed per explicit instruction). Intended for review once the framework is reinstalled and reviewer subagents are available again.

**Context:** a live testing session against `deploy/hub/crucible-hub` surfaced a series of UI/UX refinements, discussed and mocked up turn-by-turn before implementation. This log records what changed, file by file, so a future review pass doesn't have to re-derive intent from the diff alone.

---

## Design decisions this implements (summary, see full mockups in conversation)

1. Main menu: numbered-options only — no Status block, no tool-warning banner, no first-run hint. Numbers `1.` style, cyan. Wider label→description gap, description dimmed.
2. Status (new standalone screen, menu item 1): checkmark leads the domain name; "installed"/"partially installed" word dropped when a glyph is present (redundant); "not installed" kept as text (dimmed) since no glyph substitutes for absence. Fixes the "(no backend)" bug — that parenthetical no longer prints when the domain isn't installed at all.
3. Doctor: Status block removed entirely (now Status screen's exclusive job). Required tools get a leading ✓/✗ glyph instead of trailing "ok" text. Accounts checkmark leads the account name. "used by: ..." lines dimmed. `Summary:` line omitted entirely when nothing is wrong (redundant against all-green checkmarks) — only appears when there's a real problem.
4. Accounts: same checkmark-leads-name fix as Doctor. Numbered submenu items `1.` style, cyan.
5. List: restructured — domain sub-headers within each status group (Installed/Available/Diverged); technology dev+reviewer pairs collapsed to one name (`Python`, not two "agent developer"/"agent reviewer" rows); the 8 review lenses itemized by name (they're meaningfully distinct, unlike pure plumbing); the remaining ~30 baseline items (flows, specialists, build/review facades) collapsed to one `Framework baseline (N items)` line per domain — verified no double-counting between the lens bucket (14 = 8 reviewers + 6 rubric standards) and the baseline bucket (30 = everything else). PM/GTD's 3-item baselines stay as one line each (no natural sub-category to split on).
6. Checklist widget: `[x]` selected glyph recolored blue (was uncolored/dim) — matches the existing "+"/blue "will be added" semantic already used elsewhere, rather than introducing a second meaning for green.
7. Universal nav-hint rendering: `b: back` / `q: quit` / `?: help` rendered as a real vertical dimmed list under the header, replacing the old inline wrapped `(b: back · q: quit · ?: help)` parenthetical.
8. Universal screen-return behavior: List/Doctor/Status now block on an explicit key (honoring `b`/`q`/`?`, matching the existing nav model) with a `Press 'b' to return to the menu.` prompt, instead of auto-redrawing the Main menu immediately underneath the screen's own content. Accounts already blocks on its own numbered prompt, so no separate trailer was needed there.
9. Two stale-reference fixes unrelated to the above but found during migration verification: `flow-tech-pair` + its 2 generator agents + 3 templates still hardcode old `roles/`/`operations/`-style paths; `procedure-git-auth`/`procedure-jira-auth` `SKILL.md` descriptions still claim to live under `roles/common/skills/accounts/`.

## File-by-file changes

**Status:** implementation complete, directly by the orchestrator (no subagents installed at the time — the framework was mid-migration; no self-review performed per explicit instruction). Smoke-tested end to end against real scratch targets (install-all, List, Status, Doctor, Accounts, uninstall-all all exercised with real multi-domain state), but NOT adversarially reviewed. This is exactly what should get a `shell-script-reviewer` + lens pass once the framework is reinstalled and subagents are available again.

### `lib/hub-render.sh`
- Replaced `hub_print_header`'s inline-wrapped `(b: back · q: quit · ?: help)` parenthetical with a real vertical list (`hub_print_nav_hint_list`) — three separate dimmed lines. Dropped the width-computation/wrap logic the old inline form needed (no longer applicable; each line is always well under 80 columns).
- `hub_nav_hint_text`/`hub_nav_hint` kept (still used by `hub_confirm_gate`'s inline prompts elsewhere), but no longer used by `hub_print_header`.
- Removed `hub_main_menu_divider` (dead — superseded by every screen now blocking on `hub_press_key_to_continue` instead of auto-redrawing with a divider).
- Added `hub_dim_absent` — the "absent state gets no glyph and is dimmed" helper, used by Status.

### `lib/hub-nav.sh`
- `hub_press_key_to_continue`: now the pause for **every** screen (List/Doctor/Status gained it; it already existed for Install/Uninstall Result screens). Message changed from `Press Enter to continue (b: back · q: quit · ?: help)` to `Press 'b' to return to the menu.` — no longer repeats the nav-hint list, since the header above already shows it.

### `lib/hub-checklist.sh`
- `[x]` selected-checkbox glyph recolored blue (`hub_c 34 x`), matching `+`'s "will be added" meaning elsewhere — was previously uncolored. `[!]` (diverged) and `[ ]` unchanged.

### `crucible-hub`
- Main menu (`ch_main_menu_once`): removed the Status block, the tool-warning banner (`ch_tool_warning_banner`, deleted — dead code, was Main-menu-only), and the first-run hint (`ch_nothing_installed`, deleted likewise). Menu is now header + 9 numbered items + one dimmed hint line + prompt, nothing else.
- Numbered items: `1)` → `1.`, colored cyan; wider gap before each item's `— description` clause, which is now dimmed.
- Deleted `hub_main_menu_status_screen` — item 1 now dispatches straight to `hub-status.sh` via `ch_capability`, same as items 2/3, since Status now owns its own header + pause internally (see below) rather than the Main menu printing a header and pausing on its behalf.
- `ch_accounts_submenu`: numbered items `1.`-`4.` cyan; no separate press-key-to-continue added (the existing `Select [1-4]` prompt already blocks).
- Removed the post-dispatch `case $ch_choice in 1|2|3|4) hub_main_menu_divider ;; esac` — each screen now handles its own pause internally.

### `hub-status.sh`
- Sourced `lib/hub-nav.sh` (new dependency — needed for the interactive pause).
- Now prints its own header (`hub_print_header 'Status'`) and, when interactive, its own `hub_press_key_to_continue` pause with exit-3 propagation on quit — previously this was the Main-menu wrapper's job; Status is reachable both via the menu and directly (`crucible-hub status`), so it should behave identically either way.
- Text rendering: glyph now leads the domain label (`✓ Software Development: (2/9 technologies)`, was `Software Development: ✓ installed (2/9 technologies)`) — the redundant "installed"/"partially installed" word is gone, the glyph already says it. `not installed` is dimmed, no glyph (absent is expected, not a failure). **Fixed a real bug found in testing:** a domain with no possible detail (GTD) rendered as `✓ Getting Things Done:` — a dangling colon with nothing after it once installed. The colon now only prints when there's a detail to attach.
- `lib/hub-state.sh`'s `hub_domain_detail`: the pm-backend branch's `(no backend)` fallback text is gone — it only ever fired when Project Management wasn't installed at all (the empty-selection rule makes "installed with zero backends" unreachable), so it was just a second, confusing way of saying "not installed." Now prints nothing, matching the `*)` arm's existing "nothing to say" behavior.

### `hub-doctor.sh`
- Sourced `lib/hub-nav.sh`.
- Required-tools rows: glyph now leads (`✓ Git`, was `Git    ok` with no glyph at all for the passing case; the missing case already had `✗` leading, unchanged). Dropped the label-column-width padding computation (no longer needed once nothing follows the glyph+name on the passing case).
- `Summary:` line is now omitted entirely when there are zero problems and zero notes — previously printed `Summary: ✓ everything checked is healthy`, redundant against a screen that's already all green checkmarks.
- Added the interactive pause at the end (same pattern as List/Status).
- (Doctor never actually rendered a Status/domain block in the first place, despite earlier feedback suggesting otherwise — verified directly in the code; nothing to remove there.)

### `hub-accounts.sh`
- `status` text rendering: glyph now leads the account name (`✓ GitHub   authenticated as ...`, was `GitHub   ✓ authenticated as ...`); the no-glyph branches (`not checked`, `not authenticated`, `gh not installed`) get a matching indent so labels still align, and are now dimmed via `hub_print_hint`. The `used by:` lines are dimmed the same way.

### `hub-list.sh` (the largest change)
- Sourced `lib/hub-nav.sh`.
- Complete rewrite of the text-format grouping (env/json outputs are byte-for-byte unchanged — still flat, per-unit, full granularity, since the collapsing below is a human-scan concern only):
  - **Domain sub-headers** within each status group (Installed/Available/Diverged) — a domain's sub-header only appears when it has at least one row in that status.
  - **Technology pairs collapse to one row** (`Python`, not `Python agent developer` + `Python agent reviewer` + `Python standard` as three lines) — built from `HUB_GROUPS`' own per-group aggregate state (`hub_group_state`) and label directly, NOT from `HUB_ROWS` (which deliberately keeps a technology non-atomic for Uninstall's own, different granularity needs — reused as-is, untouched).
  - **The 8 lens reviewers are itemized by name** (`Security review lens`, etc.) — classified purely by SRC PATH against `HUB_SD_DIR_LENS_REVIEWERS` (the same test `lib/hub-discovery.sh`'s own display-naming pass already runs), never a name list.
  - **Everything else in a domain's baseline collapses to one `Framework baseline (N items)` line** — `N` computed dynamically per real render, never hardcoded (verified: 36 for Software Development once its 8 lens reviewers are pulled out of the 44-unit baseline, 3 each for Project Management/GTD, all recomputed live from `HUB_STATES`).
  - **Bug found and fixed during testing:** the first version tried to also itemize each lens's own rubric *standard* by deriving a shared "lens key" from both the reviewer's and the standard's name and pairing them up — this broke immediately on the one real name mismatch in the tree (`lens-test-quality-reviewer` binds `standard-testing`, not a `standard-test-quality` that doesn't exist), producing a fake 9th "Testing review lens" entry. Fixed by not pairing at all: only lens *reviewers* are itemized (using their own precomputed display name and own unit state directly), and every rubric standard folds into the baseline count instead — the same treatment `standard-python` already gets on the technology-selection screen. Zero name-matching, zero fragility.
  - Interactive pause added at the end, same pattern as the others.

### Non-hub, tracked separately per the user's explicit request
`software-development/agents/specialists/tech-developer-generator.md`, `tech-reviewer-generator.md`, `flows/flow-tech-pair/SKILL.md`, `templates/tech-pair/template-{standard-tech,tech-developer}.md`, `accounts/procedure-git-auth/SKILL.md`, `project-management/agents/project-manager/skills/procedure-jira-auth/SKILL.md` — stale `roles/`/`operations/`-era path references and descriptions, fixed to the current domain paths. Unrelated to the hub CLI; noted here only because they were fixed in the same working session.

### Zero-hardcoding verification
Every classification added above (technology collapse, lens-reviewer itemization, baseline exclusion) is driven by `HUB_GROUPS`' own aggregate state or by SRC-PATH matching against `lib/hub-domains.sh`'s existing structural constants (`HUB_SD_DIR_LENS_REVIEWERS`) — grepped the diff directly: no new agent/skill/lens name appears literally anywhere in `hub-list.sh` or any other touched file. Adding, removing, or renaming a technology/lens/flow within an existing domain still needs zero hub changes.

## Brief the reviewers about this (running list — nothing should fall between the cracks)

Everything below is a live-testing finding that is either intentionally deferred past this implementation round, or a design tension worth a second, adversarial set of eyes once `shell-script-reviewer`/`lens-clean-code-reviewer` are available again. None of it blocks the current state; all of it should be explicitly on the review brief.

1. **No shared glyph/color component.** `hub_c CODE 'char'` calls (green `✓`, orange `!`, yellow `○`, blue `+`, red `-`) are scattered as individual one-line functions in `lib/hub-render.sh`, each hand-written rather than driven by one small registry (glyph → meaning → color). Low risk today (one file owns them all), but every new status concept has grown this ad hoc, and it's the first place a future "does orange mean the same thing everywhere" audit should look.
2. **Numbered-choice coloring is NOT unified.** `crucible-hub`'s Main menu / Accounts submenu color their own `N.` items inline (`hub_c 36 'N.'`); `lib/hub-checklist.sh` now does the identical thing with its own separate inline expression (added this session, to fix the specific "cyan `1.` in some places, plain `1)` in others" bug reported live). These are two independent implementations of the same convention with no shared helper — a real DRY gap the user explicitly flagged as something to fix at review time, not now.
3. **No shared "list things in groups, not raw" formatting logic.** `hub-list.sh`'s domain-grouped/lens-itemized/baseline-collapsed rendering and `hub-install.sh`'s near-identical (but not code-shared) domain-grouped/itemize-only-what-changes preview logic are two hand-written, structurally similar but independently-implemented bucketing algorithms. The user explicitly asked that, going forward, "when we list, we always list consistently in a grouped, not raw fashion" — ideally via ONE common formatting implementation both (and any future listing screen) call, rather than each screen re-deriving its own grouping/collapsing rules. Worth a design pass at review time: is there a real shared abstraction here, or are List's and Install's needs different enough (scan-everything vs. only-what-changes) that forcing one implementation would be the wrong call?
4. **Result screen `--details` still renders a flat, ungrouped list** for both `hub-install.sh` and `hub-uninstall.sh` — explicitly deferred this session (needs the result data to carry group/domain info it doesn't track yet). Same "grouped, not raw" principle as #3 applies here once it's tackled.
5. **This session's largest, least-reviewed diff is `hub-install.sh`'s new bucketing machinery** (`hi_bucket_reset`/`hi_bucket_add_unit`/`hi_bucket_add_selectable`/`hi_bucket_walk_group`/`hi_preview_domain`/`hi_domain_pending`) — non-trivial POSIX `sh` with `awk`/`ENVIRON` plumbing, written and smoke-tested directly (real scratch-target installs, forced divergence, forced "everything already installed") but with NO adversarial review. `shell-script-reviewer` should look hard at quoting, the TAB-safety of every new intermediate file, and whether the "already-installed items are invisible to the interactive checklist" change (this session's last fix) has any other call site that assumed a fully-installed group could still appear in a selection file — it should not, but this was verified by direct testing, not proof.
6. **A known, disclosed simplification**: the "N other technologies/standards already installed, unchanged" trailing note in Install's preview is computed by re-scanning every selectable group's live state independently of what the user selected (see `hi_preview_domain`'s own comment) rather than any single source of truth — correct by construction, but it is a second place (alongside `hi_selection_rows`) that now decides "is this group done", and a future change to what "done" means has two call sites to update, not one.
7. **Path-reference audit is NOT complete.** Only the specific files hit during earlier migration verification (`flow-tech-pair` + its 2 generator agents + 3 templates, `procedure-git-auth`/`procedure-jira-auth` `SKILL.md` descriptions) were fixed; there has been no exhaustive sweep of the whole tree for stale `roles/`/`operations/`-era path references. Flagged explicitly by the user as a "do not forget" — a full audit is still owed, separate from the hub UI effort.
8. **Everything in this file and its "File-by-file changes" section above** was implemented directly, without a self-review pass, per the user's standing instruction for this entire live-testing effort. All of it — not just the items above — is in scope for the first real review pass once reviewer subagents are available.

## Review cycle — CLOSED 2026-08-01

The review this section was written to set up ran once reviewer subagents came back online: a full-audit swarm (shell-script-reviewer + all 8 lenses: clean-code, consistency, security, compatibility, observability, performance, persistence, test-quality) against the whole of `deploy/hub/`, followed by 5 rounds of fix → re-verify via the shell-script-developer/shell-script-reviewer tech pair, ending in a clean `APPROVED` with zero open findings. A parallel repo-wide audit also swept every `.md` file for stale pre-restructuring path references (fixed 3 files: `software-development/agents/developers/tests-developer.md`, `CONTINUATION.md`, `README.md`; left dated/archival records untouched on purpose).

**Real defects found and fixed** (not an exhaustive list — see the individual round reports for full detail):
- **Data-safety (CRITICAL/HIGH):** `hub_bundle_remove`'s restore step ran even when the config unlink was `foreign-blocked`, so `cp -RP` could overwrite a foreign occupant (writing *through* it if it was itself a symlink) and then delete the only backup in the same step. `--restore-backup=none`/a bad timestamp were silently ignored whenever exactly one backup existed. `install --apply` could die mid-apply, after taking the user's consent, on a `--source` with no root `CLAUDE.md`.
- **Security (HIGH):** the four interactive Accounts subcommands (`switch-github`/`reauth-github`/`configure-jira`/`reauth-jira`) executed a script discovered under `--source` with zero trust gate, unlike the read-only `status` path. Fixed with one shared gate now covering all five delegate sites, including an ownership + group/other-writability check on both the script file *and* its containing directory.
- **Correctness (confirmed independently by 4 reviewers):** `hi_preview_domain` double-counted an already-installed technology's standard on `--all`/flag-driven runs, and under-counted it to zero on the interactive path — root-caused precisely (two loops with disjoint-in-theory-but-not-in-practice conditions) and fixed so both paths now count exactly once.
- **Correctness (auth reporting):** `HA_RAN=1` was set unconditionally after running a delegate, so a crashed or ambiguous-result auth probe rendered as a false "authenticated" checkmark — found independently by both the security and observability lenses from different angles.
- Plus: an unreachable domain-checklist state (`b` from the confirm screen became a silent no-op), a critical-tier prompt that `die`d on a bare Enter instead of applying its documented default, a `set -e` abort on a zero-candidate discovery source, an ellipsis-truncation column miscalculation under `LC_ALL=C`, a temp-workspace leak on every `exec`-based delegate, several color-constant gaps (the "safe" confirm tier, one y/N prompt, one numbered list), multiple stale comments referencing functions deleted in earlier rounds, and a duplicate-outcome-line cosmetic bug in the bundle-restore-blocked path.

**Deliberately not fixed, by explicit instruction:** the compatibility lens's spec-vs-code drift findings (Doctor's new Diverged section, the `HUB_CORE_*`→`HUB_BUNDLE_*` rename, etc.) — the user determined the published spec drafts are themselves stale and the code is authoritative, so no code changes were made to chase them. Also out of scope: writing an automated test suite (the test-quality lens found none exist for this CLI at all — a real gap, but `flow-testing` fires only on explicit human confirmation, never as a review side-effect) and the performance lens's algorithmic-complexity findings (explicitly assessed by that lens as non-gating "stops the growth curve" work, not urgent).

**Verification discipline:** every fix round was smoke-tested end-to-end on real scratch targets (not just reasoned about) by the implementing agent, then independently re-derived from the actual code by a fresh reviewer agent with no access to the developer's own report — including re-tracing the standards double-count fix from scratch against both failure scenarios, and reproducing the bundle duplicate-line bug in a scratch copy before/after to prove the fix.

## Round 3 — already-installed exclusion, action-hint-on-the-prompt-line, shared color constants

Implemented directly, per the same standing instruction, immediately before the first real review pass this round triggers.

- **`hub-install.sh`**: `hi_selection_rows` now excludes any group that is already fully installed from the technology/backend checklist entirely (was: listed, annotated "already installed", still selectable — a real bug: selecting it changed nothing). `hi_select_interactive` now distinguishes "genuinely no candidate of this kind exists" (drops the domain, as before) from "candidates exist but are all installed" (keeps the domain selected — its baseline may still be pending — and skips straight past the now-empty sub-selection step). `hi_preview_domain`'s "already installed, unchanged" counts now come from an independent scan of every selectable group's live state, not from what the user happened to select — the interactive checklist can no longer surface an installed key at all, so that count has to be computed a different way than the flag-driven path's.
- **Shared color constants** (`lib/hub-render.sh`): `HUB_KEY_COLOR` (bold cyan, `hub_key`) for any literal key/word/phrase the user may type; `HUB_NUMBER_COLOR` (plain cyan, `hub_number`) for numbered choices; `HUB_NEW_COLOR`, `HUB_DANGER_COLOR`, `HUB_CRITICAL_COLOR` extracted from previously-scattered inline `hub_c 34/33/31` calls in `lib/hub-checklist.sh`, `lib/hub-nav.sh`, and `hub-uninstall.sh` that had silently drifted into their own private copies of an existing color. Every shortcut letter/word (`b`, `q`, `?`, `a`, `n`, `/text`, `Enter`, the uninstall-all confirmation phrase) now renders via `hub_key`, everywhere it appears. (`/text` was omitted from this list when it was first written, even though `lib/hub-nav.sh`'s help screen already colored it via `hub_key`; corrected here. A later round split the treatment by ROLE rather than by token: `/text` stays `hub_key` on the help screen, which is read-only reference content, and moved to `hub_hint_segment` on the checklist's live hint line, along with every other key in a trailing hint list.)
- **"The `>` line contains the action hint"** — the rule a live test session settled on for every input point in this hub. `hub_print_header` no longer prints a standalone `b: back / q: quit / ?: help` list under the title (removed `hub_print_nav_hint_list` / `hub_nav_hint_text`, both now dead); each screen's own final prompt carries its full, accurate action hint instead — `hub_nav_keys_hint` is the one shared builder for the "b/q/?" trio, appended by `hub_checklist_hint_text`, `hub_confirm_prompt`, and `hub_press_key_to_continue` (which also now leads with `Enter`, not `b`, since Enter was always the real default and the old wording implied `b` was required). The Main menu and Accounts submenu prompts gained their own hand-composed hints (no `b` on the Main menu — nothing to go back to). A checklist's SUBTITLE (e.g. "Which domain(s) do you want to install?") is no longer dimmed — it is the actual question being asked, not a secondary hint.
- **Explicitly out of scope, by the user's own request**: live, per-keystroke hint replacement (hint disappearing character-by-character as the user types, before Enter) was considered and declined — it requires raw/cbreak terminal input, the exact tradeoff this hub already declined once for arrow-key navigation. The achievable alternative implemented instead: the hint lives on the same line as the prompt and updates between screens, never mid-keystroke.

All of Round 3 is smoke-tested (full install-all → status → list → doctor → uninstall-all cycle on a scratch target, plus isolated rendering checks confirming every new/changed prompt's actual ANSI output) but, like Rounds 1-2, has had NO adversarial review.
