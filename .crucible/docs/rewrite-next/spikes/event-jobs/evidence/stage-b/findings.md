# Stage B findings

1. **A held events lock loses `job.assigned`** (B6, first try). The PostToolUse hook wrote through the writer's fixed ~5 s lock wait; the lock was held 12 s; the write failed with exit 6 and the hook, which cannot block a launch, went on. The agent then had no job: its writes were refused, its stop found no job, and the job stayed dispatched with no end in the running session (`orphans.sh` sees it only from another session). Lab fix: the assign hooks wait as long as the stop hook (up to 60 s). For the real build: every hook that writes an event must wait or retry past a held lock, and a hook that finally fails must leave a trace main's scan can see (the job would otherwise wait for ever).
2. **A background or resumed agent works before it is assigned** (B6, second try). PostToolUse on Agent runs while the launched agent already makes tool calls. With the lock held, the reviewer's report write came 12 s before `job.assigned` and was refused as "no open job"; it can happen without a held lock too. Lab fix: the agent-side hooks (scope, stop) wait for the agent's assignment, up to a minute, when the agent has no open job (a hot job's send hook has the same race). For the real build: "an agent with no job is refused" must mean "never assigned after the wait", not "not assigned yet".
3. **TaskStop fires no stop hook** (B7). Main stopped a working builder; the harness reported it `killed`; SubagentStop never ran, so the job stayed assigned with no end. TaskStop's `task_id` equals the agent id, so a PostToolUse hook on TaskStop can write `job.ended {reason: cancelled}` itself: a cancel then needs no line in main's prose. (B7's first try also showed a foreground `sleep` is blocked by the harness, and that an agent which can't change its tree ends as `gave-up`, as designed.)
4. **Default permission mode stalls an unattended job at its first read** (B8). With no human, a background agent's permission prompts are refused: the builder could not even read its job file. The events still held: its stop hook ended it `gave-up`. With the scope hook answering `allow` for what the job covers (reads of the effort and its tree, writes in the tree and to its report, the builder's Bash), the same job ran clean and submitted. For the real build: the scope hook is also the permission grant for job agents, and the builder's Bash grant must be narrowed to what a job may run (the lab grants all of it). Also seen: the owner's settings default to `auto` mode, which is why a first run without the flag passed; tests of permissions must pass `--permission-mode` explicitly.
5. **The scan is too slow on a long log; the writer is not** (long log, 2,001 events, 500 open "no review" roots). One write at 2,001 events took under a second (the whole fill took 460 s, growing with the log). `owes.sh` took 98 s, which a Stop hook can't afford. For the real build: the scan must not recompute every root from the whole log on every stop. Skip closed roots, and keep a per-root summary that writes update, or index by root. Reading and normalizing all 2,001 events took under a second, so the cost is the per-root rules in `owes.jq`, not the reader. The spike's live runs stay far below this size.
   **A realistic shape is fast** (`evidence/long-log/longlog-roots.sh`): 1,985 events over five roots of about 400 each, four of them closed. `owes.sh` takes 0.6 s, the whole Stop hook (`main-stop.sh`, with its orphan scan) 1.3 s, and one write under a second. Skipping closed roots, which `owes.jq` already does, is enough at this size. The 98 s case was the 500 open roots, and only an effort with that many open chains needs the summary or index.
6. **Interactive sessions have no `run_in_background` field** (live C1, run 1). There every subagent runs in the background, and the Agent tool doesn't take the field; the hook refused every job agent and main, rightly, stopped and asked. The headless runs had the field, so Stage B could not see it. Lab fix: refuse only an explicit `false`. For the real build: the old rewrite's interactive fix (#28) is the same lesson; check both modes.
