# Standard: Persistence

The **one** definition of correct persistence. Backend developers build to it (data kept correct from the first write, not repaired after a corruption incident); the `lens-persistence-reviewer` judges against it. Both bind this single skill, so there is no daylight between how we build and how we review.

**Store-agnostic by design.** The invariants below hold for **any** durable store — Postgres, MySQL, MongoDB, DynamoDB, Cassandra, Redis, Neo4j. They are written **capability-conditionally**: the *goal* is fixed, but *what counts as correct* depends on what the target store actually guarantees. Never assume SQL.

## Think in guarantees (the model)

Every durable store offers a specific set of guarantees. Correct code **matches its behavior to the store's real guarantees** — no stronger, no weaker. So the first move, for a given piece of code, is to **name the store and the two-or-three guarantees that matter here**, in one line (e.g. *"DynamoDB: single-item atomic by default — multi-item only via a bounded transaction API — eventual reads by default, conditional writes for concurrency"*).

- **Headline capabilities → trust general knowledge.** "Postgres is ACID," "Redis is single-node atomic via MULTI/Lua," "DynamoDB is single-item atomic by default," "Cassandra is eventually consistent." No lookup needed.
- **Version- or edition-conditional nuance → verify (context7/WebFetch), and only then.** The traps live here: Mongo multi-document transactions need a replica set / sharded cluster (and are discouraged on hot paths), Postgres isolation level is configurable, a driver's default read/write concern varies. Do **not** lean on a stale headline where the real answer is "yes, but only under condition X."
- **Verify whenever your one-liner would DENY a capability, not only when it asserts one.** Capabilities grow — multi-item transaction APIs, new consistency modes, added secondary-index types. Denying the store a capability it actually has (and forcing a saga where a transaction exists) is as wrong as assuming one it lacks.

## The capability axes (what to establish per store)

Read every invariant below through these six axes of the target store:

| Axis | The question | Why it changes the rule |
|------|--------------|--------------------------|
| **Transaction scope** | Multi-item atomic writes? single-item only? none? | Decides whether all-or-nothing is a transaction or a saga. |
| **Consistency model** | Strong / read-your-writes / eventual (and tunable)? | Decides whether a just-written value can be read back reliably. |
| **Constraint enforcement** | Native (uniqueness/FK/required/range) or app-only? | Decides *where* integrity rules must live. |
| **Concurrency control** | Optimistic version / conditional write / locks / none? | Decides how lost updates are prevented. |
| **Query/index model** | Secondary indexes / joins / scans? scan cost? | Decides which access patterns are safe vs a hidden full scan. |
| **Durability / ack level** | Fire-and-forget / single-node / quorum-majority / journal-fsync — tunable? | Decides at what point a write may be treated as committed vs still loseable on failover. |

## The invariants (capability-conditional)

### 1. Data integrity & consistency
- **Integrity rules live at one authoritative layer.** If the store enforces constraints natively (uniqueness, referential integrity, required fields, valid ranges) → the code MUST use them, not re-implement them only in app code. If the store does NOT (schemaless / key-value) → the rules MUST be enforced at **one** well-defined layer (a repository / write path), never scattered or left implicit.
- **No orphaned or contradictory state** — a write that leaves a reference dangling, a denormalized copy out of sync, or a required invariant broken is a defect regardless of store.
- **Validate before persist** — reject invalid domain state at the write boundary; do not rely on a later read to notice corruption.
- **Logical deletion must stay correct.** Where deletion is a soft-delete / tombstone / status flag, every live read path MUST exclude the deleted records through a **structural** control (a partial/filtered index, a generated uniqueness key, or a mandatory repository-level predicate — never a hand-remembered `WHERE`), and uniqueness / referential / cascade rules MUST account for the tombstone. A soft-deleted row that collides with a unique constraint, leaks into a live query, or bypasses a cascade is a correctness defect.
- **Preserve state the domain needs to reconstruct.** Where correctness depends on prior state (a ledger, an event-sourced aggregate, bitemporal validity, legally-required history), a destructive in-place update or hard-delete that erases recoverable prior state is a data-loss defect — keep it append-only / versioned. *(General audit logging for its own sake → observability/security; the trigger here is that correctness needs the old value.)*

### 2. Atomicity & transactions
- **An operation that must be all-or-nothing must be made so — by the store's actual mechanism.** If multi-item atomic writes are supported → wrap the operation in one. If NOT → the operation MUST be **idempotent + provide a compensation / saga path**, and the code MUST NOT silently assume atomicity the store does not give.
- **Keep transaction scope tight** — never hold a transaction open across a network call, external API, or user think-time; it starves the pool and widens lock windows (and on MVCC stores a long-running transaction — even read-only — blocks reclamation/vacuum).
- **No partial multi-write masquerading as atomic** — flag a sequence of writes that must all succeed but has no transaction and no compensation.
- **No cross-store dual-write.** A write that must land in two systems (DB + cache, DB + search index, DB + message broker) has no shared transaction. Do NOT "commit here, then write there" — a crash between the two silently loses the second (the classic dual-write bug). Record the second effect in the **same atomic unit** as the first — a transactional **outbox** / change-data-capture where the store supports it — and relay it separately; otherwise require an explicit reconcile. *(Cross-service coordination of such steps is a saga; distributed two-phase commit is discouraged — blocking and coordinator-bound.)*
- **A bulk/batch write is NOT a transaction unless the store says so.** An *ordered* bulk write can stop at the first error leaving the prefix applied and the rest not; a multi-partition unlogged batch is non-atomic; a batch API can return *unprocessed* items the caller must retry. Treat partial completion explicitly — idempotent retry of the remainder or compensation — never assume "one bulk call" is all-or-nothing.

### 3. Concurrency & isolation
- **Guard against lost updates** on any read-modify-write. Use the store's real primitive: optimistic concurrency (version / etag), a conditional write, or an appropriate lock. A naive read-then-write under concurrency silently drops one update.
- **Claim a unit of work atomically.** A worker that picks up a pending row/job MUST claim it in one atomic step — `SELECT … FOR UPDATE SKIP LOCKED`, a conditional / CAS status update, or a leased lock with a visibility timeout — never a plain read-then-update, which lets two workers claim and double-process the same item.
- **Acquire multiple locks in a consistent global order.** Where a transaction takes more than one lock, acquire them in a stable order (e.g. by primary key, parent-before-child) across every code path so a circular wait can't form — **ordering is the deadlock fix; the bounded retry in §6 is only the backstop.** Bound every lock/statement wait (a lock/statement timeout) so a blocked write fails fast instead of holding a connection indefinitely. On single-item-atomic stores this does not arise.
- **Don't assume isolation stronger than configured.** Know the store's / transaction's actual isolation or consistency level; code that assumes serializable behavior on a read-committed or eventually-consistent store is wrong.
- **A single-item lost update is not the only concurrency hazard.** The remedies above catch a lost update on ONE item. They do NOT catch **write-skew / phantom** anomalies, where two transactions each read a multi-row predicate or aggregate, both pass a check, and both write — corrupting a cross-row invariant that per-row versioning never sees. Those need serializable isolation, a predicate/range lock, or — on single-item-atomic stores, where they cannot be prevented transactionally at all — a serialized owner / saga.
- **Blind writes on last-write-wins stores can silently drop data.** On eventually-consistent / LWW stores, two concurrent blind writes to the same item lose one with no error. Require a conditional / compare-and-set write, a CRDT, or explicit version reconciliation wherever writers can collide.
- **Read-your-writes** — under eventual consistency, do not read a value back immediately and assume the write is visible unless a strong/consistent read is requested. Selecting the consistency / read-and-write concern per operation (where the store tunes it) is a required decision, not a default to accept blindly. This also covers **read-replica routing**: a read that must see a just-committed write MUST go to the primary (session-pinned for the lag window) or gate on a replication token — never assume an asynchronous replica has caught up.

### 4. Access-pattern correctness
- **Model from the access patterns on join-less stores.** Where the store has no ad-hoc joins (document / wide-column / key-value), the data model MUST be derived from the known read patterns — denormalize, add per-query tables / materialized views. A required query with no supporting index, table, or view is a **design defect**, not a tuning gap. (Relational stores lean on joins + indexes instead; either way the query must be servable without a scan.)
- **No N+1** — a query in a loop (or a lazy relation walked per row) that should be one batched / joined / eager fetch. (Framework lazy-loading is the usual culprit; the *safe eager/batch API is the control* — flag only when it is bypassed.)
- **Bounded result sets** — never fetch an unbounded collection into memory; cap it, stream it, or paginate.
- **Stable, bounded pagination** — every list path has a bound. On large or rapidly-changing data prefer **keyset/cursor** pagination: naive offset can **skip or duplicate rows** when rows are inserted/deleted mid-traversal (a *correctness* defect — the separate O(n)-at-depth cost is performance's). Keyset's own limits are real, so offset stays acceptable for small bounded sets, or when random page-jump / a cheap total-count is a hard product requirement keyset can't serve — flag offset only on large / hot / changing data.
- **Projection** — fetch only the fields/columns needed; over-fetching huge/unbounded columns (BLOBs, large documents) into memory is a bounds concern (see §7). *(Pure `SELECT *` bandwidth/scaling → `standard-performance`.)*
- **Query hits an index** — a filter/sort on a hot path must be served by an index, not a full scan. *(Whether to ADD an index and index tuning depth is the performance lens; correctness — "this hot query silently scans" — is yours.)*

### 5. Schema evolution & migrations
The goal is store-neutral: **evolve the persisted shape so old and new readers/writers coexist through the transition** — never a big-bang that assumes all code and data flip at once. How it is realized is capability-conditional:
- **Stores with DDL (relational):** versioned, ordered, tool-applied migrations (never hand-edited against a live schema), each with an up + a down or a documented forward-fix. Use **expand-contract (parallel change)**: add the new shape (nullable / no forced rewrite) → **backfill existing data in bounded batches, never one long transaction** → **dual-write both shapes during the transition** so rows written mid-backfill converge → switch the code → drop the old shape, across releases. Never a single migration that renames/drops a column the running code still uses.
- **Schemaless stores (document / wide-column / key-value):** there is no `ALTER`. Evolve app-side — a `schemaVersion` field, **tolerant readers** that accept old and new shapes, and **lazy migration on read** or a throttled background rewrite; never an unthrottled full-collection rewrite (the scan-rewrite is the schemaless analogue of a table lock). The coexistence invariant is identical; only the mechanism differs.
- **Don't assume a schema change is cheap** — a change that looks metadata-only may still take an exclusive lock or rewrite the whole dataset; establish its lock/rewrite cost and prefer the store's online / non-blocking form (or an explicit maintenance window). Keep the schema change, the data backfill, and the code deploy as **separate, independently-revertible steps**.
- **Rolling deploys run two app versions at once** — every intermediate shape must satisfy both the previous and next version. A new required field needs a default or a backfill so neither version breaks (judge by the actual lock/rewrite cost, not stale folklore about defaults).

### 6. Reliability & durability
- **Match success to the store's durability guarantee.** Treat a write as committed only at the durability level the operation requires — a write acknowledged before it is durably persisted can be silently lost: fire-and-forget / below-quorum acks (`w:0`, `acks=1`) lose it on **failover**; async *local* commit (`synchronous_commit=off`) loses it on **crash**, even with no replica. Where loss is unacceptable, require durable persistence before reporting success — local fsync/journal-ack plus quorum/majority replication as the topology needs; where every ack is already durable, this does not apply.
- **Writes are idempotent under retry** — a retried create must not double-insert. Enforce dedupe with a store-native **atomic** primitive committed *together with* the effect — a unique constraint / conditional-put on the dedupe key, **not** a check-then-write (two concurrent retries can both pass a separate check) — and persist the first outcome for replay. An upsert is idempotent only when it sets **absolute** state; an upsert that increments/appends is not. (At-least-once delivery + a non-idempotent write = duplicates. Exactly-once *delivery* across a network is unachievable — aim for exactly-once *effects* via idempotent writes; don't trust a broker's "exactly-once" claim blindly.)
- **A consumer of at-least-once messages must be idempotent** — record the processed message-id in the **same atomic unit** as its effect (unique-constraint / conditional-put on the id), and any order-dependent effect must tolerate out-of-order or duplicate delivery. (The consume-side mirror of the write-side dedupe + outbox above.)
- **Guard destructive / irreversible operations.** An unpredicated `DELETE`/`UPDATE`, a `TRUNCATE`/`DROP`/drop-and-repopulate in a migration, or an unbounded rewrite must be predicate-guarded and have a recovery path (a checkpoint / backup / PITR boundary, or a documented forward-fix) before it runs.
- **Handle partial failure** — a multi-step persistence flow must define what happens when step 2 of 3 fails (compensate, retry, or fail the whole).
- **Bounded retries with jittered backoff** on transient data-layer errors (deadlock, timeout, throttling); never an unbounded tight retry loop. Do not swallow a write error and report success.
- **TTL / expiry is best-effort** where the store says so — deletion can lag expiry by hours. Never depend on exact expiry timing for correctness, and never let a required record be silently reaped by a TTL.

### 7. Connection & resource discipline
- **Use a connection pool sized to the store's limits** — not a new connection per call, not an unbounded pool that exhausts the server.
- **Always release** connections, cursors, statements, and transactions — no leak on the error path (use the language's scoped/`try-with`/`defer`/`using` construct).
- **No unbounded in-memory materialization** — for large reads, stream / server-side-cursor rather than holding the whole set in memory (bounding the result *set* itself is §4).

### 8. Value representation & equality
- **Store values with the equality/uniqueness semantics the code relies on.** Collation / case-sensitivity, Unicode normalization (NFC vs NFD), and null-vs-absent-vs-sentinel all change what the store treats as "equal" — a uniqueness or lookup rule that assumes an equality the store enforces differently (case-folding colliding distinct keys; a sparse/unique index treating missing, `null`, and `""` as three values) is a correctness defect.
- **Use an exact representation for exact values.** Money and precise decimals MUST be persisted as an exact type — exact-decimal, integer minor-units, or string — never the store's binary float or a bare JSON number (IEEE-754 float64 in most document/KV stores), which lose precision at rest. *(In-code rounding/arithmetic → `{tech}`/clean-code; only the at-rest representation is yours.)*
- **Persist instants unambiguously** — UTC or an offset-aware type, never a naive local wall-clock value whose zone is implicit (ordering and time-window queries silently corrupt across DST / differently-configured nodes). *(Display timezone → presentation.)*
- **Keys other records reference are immutable, and the id shape fits the store's model.** Mutating a referenced key orphans references; and the id-generation shape (monotonic vs random) must match the store's partition/index model — the right choice inverts between a single B-tree and a distributed partitioned store. *(UUID-vs-sequence throughput → performance; id enumeration/IDOR → security; natural-vs-surrogate choice → architecture.)*
- **A generated key must not exhaust its value domain within the system's lifetime.** A bounded 32-bit sequence overflows (~2.1B) and then every insert fails — a total write outage. Default to a 64-bit or UUID key space; where the store uses a bounded sequence, monitor headroom and migrate to a wider type via expand-contract **before** exhaustion, never after.
- **A persisted serialized value must evolve compatibly** — an enum, polymorphic type, or JSON/Avro/Protobuf blob must still deserialize under new code (old records readable) and not break old readers mid-rollout; a removed variant that crashes on read of an old row is a correctness defect.

## Boundaries (stay in lane — point, do not restate)
- **Query-injection / unsafe query construction** (string-built queries, `$where`, unparameterized input) → owned by **`standard-security`**. Persistence points there; it does not re-list injection rules.
- **Index tuning, capacity planning, and algorithmic/data scaling depth** → **`standard-performance`**. Persistence owns access-pattern *correctness* (a hot query that silently full-scans); the scaling analysis is performance's.
- **Slow-query logging, query metrics, tracing the data layer** → **`standard-observability`**.
- **Read-path / cache coherence** (an application or read-model cache serving a value that contradicts a committed write) → consistency / architecture design. Persistence flags only the **store-level** stale read (read-your-writes under eventual consistency), not the application's cache-invalidation strategy.
- **Which store to choose / polyglot-persistence architecture** → a costly forked decision — hand to the decision pattern, not this standard.
- **Language & ORM mechanics** (JPA lazy-load semantics, SQLx compile-time checks, Eloquent/Doctrine specifics, driver APIs) → the **`{tech}` pair**. This standard defines the store-agnostic invariant; the language standard supplies the idiom.
- **Encryption at rest, secrets in connection strings, PII erasure/anonymization & data-retention policy** → **`standard-security`** / compliance. Persistence supplies the mechanism (e.g. a soft-delete does NOT satisfy a GDPR erasure); the obligation and policy are security's.
- **Backup / restore / point-in-time-recovery execution, replica topology & failover tuning, capacity/DR strategy** → **devops / ops**. Persistence owns the code-level guard (durable-ack, destructive-op recovery path); the DR infrastructure is not its lane.
- **Transaction/consistency-boundary sizing** (which invariants share one aggregate/transaction) → an **architecture / domain-modeling** decision — hand to the decision pattern. Persistence owns transaction *duration* and *atomicity*, not aggregate *breadth*.

## Persistence consistency
Conform to the project's established persistence patterns — the repository/DAO layer, the migration tool, the id/key strategy, transaction boundaries, and the read/write-concern defaults. New code should not bypass an existing safe pattern. But a genuine data-integrity or lost-update bug is a bug — project "convention" never launders data corruption.
