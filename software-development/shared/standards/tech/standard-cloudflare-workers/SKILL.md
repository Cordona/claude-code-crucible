# Standard: Cloudflare Workers

The **one** definition of what good, correct Cloudflare Workers platform code looks like — generic to any team building on Workers, not scoped to a specific project. The `cloudflare-workers-developer` builds to it; the `cloudflare-workers-reviewer` judges against it. Because both bind this single skill, there is no daylight between how we write Workers code and how we review it — a rule changed here moves both sides at once.

**This standard composes with `standard-typescript`, not against it.** TypeScript language discipline and Zod schema/validation conventions live there — this file owns only what's specific to the Workers runtime and its ecosystem (`agents`/`McpAgent`, `@modelcontextprotocol/sdk`, `jose`, Wrangler). Any pair building TypeScript on Workers binds both skills; neither restates the other's rules.

This skill defines **WHAT good looks like** — the idioms to reach for and the traps to avoid. It is **NOT a Workers tutorial**: assume fluent TypeScript, and encode only the non-default priorities and easy-to-miss pitfalls of this runtime. It deliberately does NOT contain: the builder's workflow (`build-core`) or the reviewer's machinery — the correctness-detective method, scope-boundary/handoff, severity, and `category` vocabulary live with the `cloudflare-workers-reviewer`; report envelopes live in `build-report-standards` / `review-report-standards`.

Assume **the Workers runtime deployed by Wrangler 4.x against an explicit recent `compatibility_date`; `agents` 0.3.x (`McpAgent` on a SQLite-backed Durable Object); `@modelcontextprotocol/sdk` 1.25.x; `jose` 6.x; Biome 2.x; Vitest 3.x; strict-mode TypeScript and Zod per `standard-typescript`** unless the project states otherwise.

**Framing:** each item states what **good Workers code** does and what a **defect** is — read it as a build target or a review rubric interchangeably.

## 1. The Worker execution model

The runtime is not Node and not a long-lived server. Almost every Workers-specific defect traces back to assuming one of those.

- **Module/global scope survives across unrelated requests, for an unpredictable isolate lifetime, with no guaranteed reset.** It may therefore hold only cacheable, non-secret, config-derived values — a JWKS resolver keyed by team domain is the sanctioned shape. **A defect:** any request-, user-, or tenant-scoped mutable state at module scope (a "current user", a per-request accumulator, a mutable cache of authorization decisions) — it leaks across requests and across tenants.
- **CPU time, not wall-clock, is the billed and limited resource** (30s default on paid plans, 10ms on free; paid plans can raise this to 5 min via `limits.cpu_ms` when a workload genuinely needs it). Awaiting a slow subrequest is cheap; a tight synchronous loop is not.
- **`Date.now()` and `performance.now()` do not advance during CPU execution** (a deliberate Spectre mitigation) — they only move after an I/O event. **A defect:** code that tries to self-measure its own compute time, or that spins on a clock expecting it to progress. Measure across I/O boundaries or not at all.
- **Every promise must be awaited or handed to `ctx.waitUntil()`.** A floating promise is silently cancelled the moment the handler returns. `ctx.waitUntil()` extends the invocation up to 30s **total across all calls in that invocation**, not per call — longer work belongs in Queues or Workflows. Call it as `ctx.waitUntil(...)`; **destructuring it breaks its `this` binding.**
- **`Request`, its `Headers`, and bodies are immutable / single-use.** To change a header, construct a new `Request`/`Headers`; to change status or headers on a response, use `new Response(body, response)`. `.clone()` without consuming both clones buffers the entire body and warns — `response.body.tee()` is the correct tool for genuine dual consumption, and re-reading an already-consumed body throws.
- The handler is `export default { ... } satisfies ExportedHandler<Env>` — the `satisfies` form (`standard-typescript` §1) keeps `env`/`ctx` typed without widening the export.

## 2. Routing & the HTTP surface (no router framework)

This rubric assumes **raw `export default { fetch }` Worker code, not a framework-routed API** — no router framework is assumed, and none should be introduced without the brief asking for it. (If a project genuinely uses Hono, its own conventions govern there; nothing in this file depends on it.)

- Route by **explicit method + path checks with early returns**, in a deliberate order.
- **Authentication comes before any branch that reads or mutates data, never after.** An early-return branch placed above the auth check is an unauthenticated endpoint whether or not it was meant to be, and must be commented as a deliberate choice with its exposure stated.
- Parse the path from `new URL(request.url).pathname`; never string-match a raw `request.url`.
- **CORS is validated, not echoed.** Where CORS is needed, validate `Origin` *and* `Access-Control-Request-Method` *and* `Access-Control-Request-Headers` before emitting full CORS headers, and serve an explicit `OPTIONS` preflight path. **A defect:** blind origin echo, or `Access-Control-Allow-Origin: *` on an authenticated route. Emit `Vary: Origin` on any response whose `Access-Control-Allow-Origin` varies per request — its absence lets an edge/cache layer serve one origin's cached response to another. Never pair `Access-Control-Allow-Credentials: true` with a wildcard or an unvalidated origin.
- Return real status codes with short, non-leaking bodies (`401`/`403` for auth, `4xx` for caller error, `5xx` only for genuine server failure). Never return `200` with an error payload from the Worker's own HTTP surface — that is an MCP tool-result convention (§5), not an HTTP one.

## 3. Durable Objects: concurrency & storage semantics

A Durable Object is single-threaded per instance and serializes events (~1,000 req/s soft ceiling). Its gates give you more atomicity than you expect in one place and less in another — knowing which is which is the whole section.

- **Input gates** block new events while a storage operation is outstanding; **output gates** hold outgoing responses until pending writes durably commit, so a client can never observe a success that wasn't persisted. Writes issued **with no intervening `await`** are auto-coalesced into a single atomic transaction.
- **An `await` between dependent writes breaks that atomicity.** For any multi-step read-modify-write, use `transaction()` / `transactionSync()` explicitly rather than relying on coalescing.
- **Non-storage I/O does not hold the input gate.** State can change between a `fetch()`/R2 read and a subsequent write — use an optimistic-concurrency check (compare-and-set on a version), never assumed atomicity.
- **`blockConcurrencyWhile()` blocks all concurrency unconditionally.** Correct for one-time constructor initialization; **a defect per-request** — anything costly inside it throttles the object toward ~200 req/s.
- **SQLite cursors are not a stable snapshot across an `await`.** Drain synchronously (`.toArray()`) when snapshot semantics matter.
- **Alarms can fire more than once.** Alarm handlers must be idempotent; a handler that assumes exactly-once delivery is a defect.
- Anything that must survive eviction lives in storage (`sql`, `state`, or props), never in an ordinary instance field.
- **All DO SQLite access is parameter-bound — `sql.exec(query, ...bindings)` or the `agents` `this.sql` tagged template — never string-concatenated or interpolated SQL, including for identifiers (table/column names).** A DO's own storage is not a trust boundary exemption: caller- or upstream-derived text reaching a query string unbound is SQL injection regardless of the "internal" storage layer it targets.
- **Storage capacity is per-object, not per-account.** SQLite-backed DO storage caps at 10 GB per individual object (paid; 5 GB free-plan account total), 2 MB per row/blob/KV entry, 100 columns/table, 100 KB per SQL statement. These are the ceilings any schema must fit within; schema and sharding design itself is `lens-persistence`'s call, not this section's.

## 4. `McpAgent` lifecycle & hibernation

`McpAgent<Env, State, Props>` extends `Agent`, which wraps a Durable Object — an MCP agent **is** a DO instance with SQLite-backed storage, not a plain handler. WebSocket Hibernation is on by default, and its real lifecycle is easy to misread from the API surface alone.

- **`init()` reruns on every hibernation wake — not once per agent, ever.** Confirmed directly from the shipped `agents` package source, not just documentation: `onStart()` unconditionally calls `init()` on every activation, "each time the Durable Object is instantiated or resumed from hibernation." Tool registration and anything else in `init()` must therefore be **cheap and idempotent**. **A defect:** one-time side effects in `init()` (seeding a counter, emitting an event, charging something, appending to storage) that silently repeat on every wake.
- **Watch item, not yet a rule change — confirmed against Cloudflare's own current docs, not a rumor:** as of the Agents SDK v0.20.0 / "MCP SDK v2" changelog dated 2026-07-27 (developers.cloudflare.com, Agents SDK changelog/migration guide, retrieved via WebSearch 2026-08-13), `McpAgent` is officially **"deprecated and feature-frozen"** — Cloudflare's own migration guide directs new servers to a stateless `createMcpHandler` (from `agents/mcp/server`) with no Durable Object session at all. Projects pinned to `agents` 0.3.x and the DO-hibernation architecture this section describes can keep applying this section, in full, today. But this is a 0.x package: by semver convention **any** version bump past a pinned `0.3.x` line may be breaking, not just a major-version bump — treat any `agents` upgrade at all as the trigger to re-verify this entire section, **including §5's `McpServer`-per-session isolation rule** (its mechanism — one DO instance per session — is exactly what a stateless handler removes).
- **Watch item — `@modelcontextprotocol/sdk` version bumps:** re-verify §5's `.tool()`/`registerTool()` Zod-shape distinction (it is pinned-SDK-line-specific, confirmed against source, not guaranteed to hold across a bump) and §5's `instructions`-vs-`.describe()` bullet (a newer MCP spec revision is moving away from the `initialize`/session handshake that bullet assumes) on any SDK version change.
- **On start, `this.props` is unconditionally reloaded from DO storage** — a wake carrying no fresh `ctx.props` restores the last-persisted ones. Treat props as durable identity, not as per-request input.
- **Two independent persistence tracks:** `state`/`setState()` is client-syncable but **resets on a new session/reconnect** (Cloudflare's own docs flag this); props storage survives hibernation on a separate key. Opting out of `state` entirely (`Record<string, never>`) and delegating real persistence to an external API is a **valid deliberate pattern, not an omission** — but then nothing may be stashed in `state` "just for now."
- **`agents` authenticates nothing.** `ExecutionContext.props` is not a standard Workers-runtime field; the Worker's own `fetch` handler is solely responsible for authenticating the request and setting `ctx.props` before calling `.serve(path).fetch(...)`. The `readonly`-defeating cast that assignment needs (`(ctx as ExecutionContext & { props: … }).props = identity`) is a **documented hand-off wart, not an anti-pattern** — flagging the cast is wrong; flagging an *unauthenticated* value flowing into it is right.
- Two identity models are supported upstream: Access-JWT-in-header (§6) and an `OAuthProvider`-based token exchange that also lands in `ctx.props`. Know both exist; do not assume the codebase's shape is the only one.
- Constructor-built instance fields do not survive a wake. Anything a tool handler needs must come from props, `state`, `sql`, or be rebuilt in `init()`.

## 5. MCP tools: registration, descriptions & result semantics

Tool surfaces are read by a model, not a human. Both the schema and the prose are part of the contract.

- `.tool()` is **deprecated in favour of `registerTool()`** as of SDK 1.21.1 (the `@deprecated` JSDoc tag on the legacy overloads in the installed `mcp.d.ts`, `@modelcontextprotocol/sdk` 1.25.2, retrieved 2026-08-14), but Cloudflare's own `McpAgent` docs still show `.tool()` for stateful DO-backed servers and call `registerTool()` the path for "modern stateless servers." Prefer `registerTool()` in new code; **`.tool()` in an `McpAgent` is not a defect** — do not churn it.
- **On the legacy `.tool()` overloads only: register with the Zod raw shape, never the `ZodObject`.** Those overloads type their params argument as `Record<string, ZodSchema>` only — i.e. `SomeSchema.shape`, not `SomeSchema` — and passing the object can type-check in some cases while producing a broken runtime schema. This is the single highest-frequency footgun on `.tool()`. **`registerTool()` does not have this footgun**, confirmed directly against the installed SDK source (`zod-compat.d.ts`'s `normalizeObjectSchema(schema: AnySchema | ZodRawShapeCompat | undefined)`, called from `registerTool`'s implementation, retrieved 2026-08-14 from `node_modules/@modelcontextprotocol/sdk` 1.25.2): its `inputSchema`/`outputSchema` accept either a raw shape or a full Zod schema object and normalize at runtime. This distinction is pinned-SDK-line-specific (§4 watch item covers the re-verify trigger).
- **`.describe()` is the only channel through which per-argument guidance reaches the calling model.** Write tool and parameter descriptions as **instructions to the model** ("REQUIRED: a specific sentence saying why…"), not as human field documentation. An undescribed non-obvious parameter is a defect. **`.describe()` belongs on tool-input schemas only** (`standard-typescript` §2 covers schema naming/strictness generally) — never on internal or response schemas, since those descriptions are surfaced to an LLM caller specifically; a description on a schema no model ever sees is noise.
- **Server `instructions` vs per-tool `.describe()`:** `instructions` (returned once at `initialize`) carries cross-tool, session-scoped guidance — sequencing rules, presentation rules spanning several tools. Per-tool `.describe()` carries guidance specific to that one tool's inputs. Guidance repeated verbatim across every tool belongs in `instructions`. A newer MCP spec revision has begun moving away from the `initialize`/session handshake entirely toward a stateless protocol core — not yet what the pinned SDK version implements (§4 watch item covers the re-verify trigger).
- **Two distinct error channels.** Protocol-level JSON-RPC errors (malformed request, unknown tool) never reach the model. Tool-execution failures return a normal JSON-RPC success whose *result* carries `isError: true` — the model reads and reasons about those. **Throwing from a handler and returning `{ content, isError: true }` are functionally equivalent**: the SDK catches a thrown error and converts it to the same shape. Returning explicitly buys only control over message wording and multiple content blocks — so choose for readability, and do not flag either form as wrong.
- **Argument-shape validation never reaches the handler** — Zod runs first and short-circuits to an `isError` result. Handlers need no shape-guard boilerplate; they validate only business rules the type system cannot express.
- **Progress notifications:** `progress` MUST strictly increase on every notification, even with an unknown `total`; notifications may reference only an in-flight request's token and must stop at completion. Client opt-in via `_meta.progressToken` is optional, so a defensive `if (token === undefined) return` before sending is **required, not optional**.
- **One `McpServer`/transport instance per client session, never shared across connections.** A shared instance can leak one client's responses, progress notifications, and sampling/elicitation requests to another. The `McpAgent`/Durable-Object architecture (one instance per session) is the sanctioned shape for a pinned 0.3.x architecture (§4 watch item); a defect is any path that reuses one `McpServer` across multiple client connections.
- Error text returned to the model should say what to do next ("this stack name is taken, try another"), because it becomes the model's next-turn context.
- **A tool result becomes the model's next-turn context — never reflect raw upstream or caller-supplied text into it uncritically.** The control is **summarizing untrusted content into a fixed shape** (extract the fields you need, discard the rest as free text). Delimiting and labeling raw text as untrusted data is defense-in-depth only, not a substitute — a crafted upstream string can still steer a model even inside delimiters. This applies to `content`, `isError` text, and the server's `instructions` field alike: any of the three can become an indirect-prompt-injection sink into a tool-wielding model if untrusted text is passed through unlabeled.
- **Capability-scoping is a separate, mandatory control, not a restatement of summarization — it applies a stricter, narrower escape.** Fixed-shape summarization (the bullet above) narrows the injection risk but does not eliminate it — a free-text field extracted "into a fixed shape" can still carry a crafted instruction. Check the full three-leg "lethal trifecta" on every `McpServer`: **(1)** a tool reads/reflects untrusted upstream or caller-supplied content, **(2)** the untrusted-reading tool itself, or any co-registered tool on the same `McpServer`, can read private/sensitive data, and **(3)** another tool on the same server can produce an externally-observable side effect (an outbound HTTP call, a write to a destination outside this session, a message send). **When all three legs are present on one `McpServer`, the untrusted-reading tool's output MUST be restricted to non-free-text fields only** — enums, IDs, booleans, numeric or date values, or a short server-controlled allowlist of strings — with **zero passthrough of free-form upstream text**, even summarized. Plain fixed-shape summarization is necessary but **not sufficient** here: a summarized free-text `title`/`description` field satisfies the summarization bullet while still being a live injection vector once every leg of the trifecta is present. A defect is any three-leg-satisfying `McpServer` whose untrusted-reading tool emits any free-text field.

## 6. Auth boundary: Cloudflare Access JWT verification with `jose`

The Worker's `fetch` handler is the only authentication boundary in this architecture (§4) — everything downstream trusts whatever it sets. Hold it to full rigor.

- **Validate the `Cf-Access-Jwt-Assertion` header, never the `CF_Authorization` cookie** — the cookie is not guaranteed to be sent.
- **`createRemoteJWKSet` returns a stateful, per-instance resolver** with its own cache and refetch cooldown. Hold **one instance per team domain at module scope** and reuse it; `kid`-miss-triggered refetch (throttled ~30s) then handles key rotation transparently. **A defect:** constructing a resolver per request — it defeats all caching and hammers the JWKS endpoint.
- **The JWKS URL / team domain is static configuration — an `Env` var or module constant — never derived from a token claim, a header, the path, or any other request-derived value.** Building the verification endpoint from anything the caller influences lets an attacker point verification at a JWKS they control, passing every signature check regardless of pinned algorithms or audience checks. Check this first: it beats every other mistake on this list for impact, because an attacker who controls the JWKS also controls the claims those checks act on.
- **Every token is verified with its own correct, distinct `audience`.** Where two tokens are in play (e.g. a policy AUD and a separate stack/application AUD), each gets its own `jwtVerify` options — never the same options object reused for both, and never a call that omits `audience` for one of them, which silently accepts a token minted for a *different* Access application. Skipped audience validation is the most dangerous *claims-level* mistake (second only to a request-derived JWKS source, above) — a cryptographically valid token for another service is still an attacker's token. Two tokens sharing an issuer should resolve through the **same cached resolver**, not two redundant ones.
- **Pin `algorithms` explicitly** as defense-in-depth against algorithm-confusion (RS256→HS256 downgrade using the public key as an HMAC secret), even though `jose` structurally rejects `alg: none`. No unexplained non-zero `clockTolerance`.
- **Fail closed, independently, per token.** A missing or unverifiable token yields `401`/`403` — never a silent degrade, and never a fallback that trusts only the first token's claims when a second is absent.
- **"Signature valid" is not "claims valid."** Verify issuer, audience, expiry, *and* the claims you actually act on (a missing `email` on an email-keyed authorization model is a hard failure, not an `"unknown"` default). Never trust a decode-only helper's output.
- **Never log a raw token or a full decoded payload.** Log outcome plus low-sensitivity fields — a structured `{ src, event: "auth_denied", reason, error }` JSON line is the model shape, and both tokens get their own independently logged outcome.
- Any adjacent manual secret comparison (a service-auth header, an HMAC) uses a named constant-time primitive — `crypto.subtle.timingSafeEqual` (equal-length inputs) or an HMAC-both-sides-then-compare — never `===` and never a hand-written comparison loop, which is non-constant-time in practice regardless of intent.
- **A dev-only auth bypass must be a source literal, not runtime- or build-time-substituted.** Gating it on "the real token being absent" is not a real control — that is the unauthenticated-request condition itself. Neither a runtime flag set outside `wrangler.jsonc` (a dashboard var, a `wrangler secret`) NOR a build-time `define` substituted per environment is provable from source — a `define` flipped on in one `env.<name>` block satisfies "it's a literal constant, dead-code-eliminated" while reintroducing exactly the gap this rule exists to close. The condition must be a literal written directly in the source file, loudly logged when it fires, with nothing outside that file able to change its value, **and that literal must be `false` in committed source** — provenance alone is not the rule: `const DEV_BYPASS = true` committed directly, loudly logged, satisfies "source literal, nothing outside the file changes it" while being a live production auth bypass. A reviewer who cannot prove both the provenance AND the committed value — including checking for a per-environment `define` — treats that as a defect, not an acceptable gap.
- **A service-binding request is untrusted input like any other, not evidence the caller is internal.** It carries no `Cf-Access-Jwt-Assertion` by construction (§9) — the receiving Worker verifies the service-auth header fail-closed via the constant-time compare above, and never treats "no Access JWT arrived" or "this came over a service binding" as proof of an internal, trusted caller.
- **Authentication is not authorization.** Verifying the token proves *who* is calling; it does not prove they may act on the *specific resource* requested. Every tool or route that acts on a caller-supplied resource id (a stack name, a project id, a record key) must independently verify the verified `ctx.props` identity is permitted to act on that exact resource — deny-by-default, not deny-if-explicitly-forbidden. Identity, role, and tenant come from `ctx.props` only, **never** from a tool argument or a request field the caller controls — a `userId`/`role` parameter accepted from the caller and trusted is the same class of defect as skipping `audience`.

## 7. Errors & failure modeling

- **Domain errors are classes named `{Domain}Error`**, carrying an HTTP status (and optionally a code), and are **thrown, never returned as raw strings**. Set `this.name` explicitly — bundled/minified class names are not a reliable discriminator.
- **A Zod validation failure becomes a typed, status-coded domain error, thrown — the same as any other shape mismatch from external data** (`standard-typescript` §2 requires the conversion generally; this is what a Workers codebase converts into). The one deliberate exception: cross-field business-rule validation that Zod's type system cannot express returns a plain `string | null` — narrow, intentional, and not to be "fixed" into a throw.
- Narrow caught values before use: `err instanceof Error ? err.message : String(err)`. A bare `catch (e)` whose `e` is used as a string is a defect.
- **Never swallow.** A caught error either becomes a typed domain error, an HTTP response, or an `isError` tool result — never a logged-and-ignored no-op, and never a `null` that a caller reads as "empty."
- Error messages name the failing operation and the actionable cause; they never carry a token, a secret, a full upstream body, or an internal URL.
- Retry only idempotent operations, with a bounded budget — remember the subrequest limits (§9) and that an alarm may already be retrying you (§3).

## 8. Secrets, bindings & environment configuration

- **Never hardcode a secret, API key, token, or connection string in source or in `vars`** (CWE-798) — it must live behind `wrangler secret put` or a Secrets Store binding. A hardcoded value is not "faster for now"; it ships to every environment and every reader of the repo.
- **Three distinct secret mechanisms, chosen deliberately:** `wrangler secret put` (per-Worker, hidden after set), a **Secrets Store binding** (account-level, shared across Workers, **async `.get()`**), and plain `vars` (plaintext in config — non-sensitive values only). Code that must accept either a plain string or a Secrets Store binding resolves it through one small helper, never inline at each call site.
- **Never log a secret value.** The platform hides secrets, but that protection is bypassed entirely by the Worker's own code — `console.*` output is dashboard-visible.
- **Named environments do NOT inherit top-level bindings.** Every binding and var must be re-declared in each `env.<name>` block of `wrangler.jsonc`, or the deployed Worker silently lacks it and fails only at runtime, only in that environment. This is the highest-value config check in the file; treat a new binding added without touching every environment block as a defect.
- **`compatibility_date` / `compatibility_flags` lock in runtime behavior.** A stale date silently misses default improvements; a careless bump can silently change relied-upon behavior. Change it deliberately, in its own change, and say what it buys.
- **`Env` is generated, not hand-written** — `wrangler types` regenerates `worker-configuration.d.ts` from `wrangler.jsonc`. Re-run it after any binding/var change; a stale `Env` type is a real, recurring drift symptom. Do not hand-edit the generated file. Bindings are typed via this generated `Env` and injected — a module reaching for a global binding instead of the `env` it was handed is a defect.

## 9. Outbound I/O & network boundaries

- **`fetch(userSuppliedUrl)` is SSRF unless proven otherwise.** Allowlist scheme and host, and do not blindly follow redirects — a permissive default `redirect: 'follow'` can silently walk right past a domain allowlist to wherever the first hop redirects. This has real, repeated precedent in the Workers ecosystem: **CVE-2025-6087 / GHSA-rvpw-p7vw-wj3m** (github.com/advisories/GHSA-rvpw-p7vw-wj3m, retrieved 2026-08-13 — `@opennextjs/cloudflare`'s image-proxy fetched attacker-supplied URLs unchecked and served them under the victim's own domain), and **CVE-2026-3125 / GHSA-c7mq-gh6q-6q7c** (github.com/advisories/GHSA-c7mq-gh6q-6q7c, retrieved 2026-08-13 — a later path-normalization bypass in the same package that let a blocked path slip past edge interception) — allowlisting has to survive both "wrong URL" and "right-looking URL that isn't."
- **Never redirect or forward the caller's browser to a caller-supplied target** (a `?next=`/`?redirect_uri=`-style parameter, an OAuth callback target). Allowlist the destination, or resolve it through a server-side key→URL map — this is a distinct sink from the `fetch()` rule above (one sends the Worker somewhere, this sends the caller's browser somewhere) and matters most where an `OAuthProvider` token-exchange identity model (§4) is in play: **GHSA-2h78-5wx8-jccc** (github.com/advisories/GHSA-2h78-5wx8-jccc, retrieved 2026-08-13 — `cloudflare/workers-oauth-provider`) is a real open-redirect-plus-CSRF advisory from exactly this — an unvalidated redirect target embedded in the OAuth `state` parameter.
- **Subrequests are limited** (10,000/request on paid, 50 on free — both raisable via Wrangler config, up to 10M on paid) and only **6 outgoing connections** may await headers simultaneously — fan-out must be bounded and batched, never an unbounded `Promise.all` over a user-sized list.
- **Prefer a service binding over a public-edge round trip** for worker-to-worker calls; it bypasses the public edge (and Access) and needs only the service-auth header — verified fail-closed on the receiving end per §6's service-binding rule, never assumed trusted because of the transport. Keep the direct-HTTPS path as an explicit, commented fallback for local dev.
- **Upstream calls live behind a thin client wrapper class** — constructor-injected `env`, one method per operation, explicit status handling, response parsed through a Zod schema, failures thrown as a typed domain error. No raw `fetch` scattered through handler or tool code.
- **There is no built-in per-IP rate limiting**, and Cloudflare's own Rate Limiting binding is explicitly "permissive, eventually consistent" — its docs advise against a raw-IP key (it punishes shared NAT), and it is never a hard security control on its own.
- **The auth-verification path and any expensive or abusable MCP tool must have a bounded anti-automation check, on an identity/API-key dimension — never left unthrottled on the assumption the platform handles it.** A missing check on the token-verification path (credential-stuffing/brute-force against `jwtVerify`) or on a tool that fans out, calls an upstream, or is otherwise costly per-invocation is a defect; the check itself need not be the platform Rate Limiting binding (see above) but must exist somewhere in the request path.
- Apply an explicit timeout/abort to outbound calls that a user is waiting on; a hung subrequest burns the invocation, not just the call.

## 10. Cold-start & CPU-budget hygiene

Language-level cost only — algorithmic complexity is `lens-performance`'s job, not this file's.

- **Module scope runs on every cold start.** Keep it to cheap constants and lazily-built caches (§1); heavy parsing, large table construction, or eager network setup at module scope taxes every isolate spin-up.
- **Build expensive, reusable objects once and memoize them** (the JWKS resolver, compiled regexes, `Set`/`Map` lookup tables) — never per request.
- Prefer a `Set`/`Map` lookup over repeated array scans in a hot path; prefer streaming a body through over buffering it when the whole payload is never needed at once.
- Do not `await` sequentially what can be awaited concurrently — but bound the concurrency (§9).
- You **cannot** self-measure compute time from inside the Worker (§1). Performance claims come from observed latency across I/O or from platform metrics, never from an in-Worker stopwatch.

## 11. Naming, file layout & comments

- **One concern per file**, small single-purpose functions, **verb-first function names** (`resolveStackRole`, `parseRequestPath`, `verifyAccessJwt`).
- **`UPPER_SNAKE_CASE` for lookup-table and tuning constants** (`MANAGED_TEMPLATES`, `POLL_INTERVAL_MS`), PascalCase for classes and Zod schemas (`standard-typescript` §2), `camelCase` for everything else.
- **Comments are sparse and explain WHY, not WHAT** — a comment earns its place by recording a non-obvious constraint, a deliberate omission, a cross-repo mirror, or a link to the doc that justifies the shape. A comment restating the code below it is a defect; so is an undocumented deliberate deviation (an intentionally omitted enum value, a route that bypasses auth on purpose).
- Numeric literals with meaning are named constants with units in the name (`POLL_DEADLINE_MS`), not inline magic numbers.
- Public/exported surface is the minimum that callers need; helpers stay module-private.

## 12. Lint, format, types & test-mode discipline

- **Biome is the linter and formatter** (`recommended` preset, no custom rule overrides): 2-space indent, 100-column width, double quotes, semicolons always, trailing commas everywhere.
- **Biome lints `src/**/*.ts` only — not `test/`.** Test files are formatted consistently by habit, not enforcement; do **not** hold them to a Biome gate or treat their formatting as a finding.
- The clean bar: **`tsc --noEmit` with zero errors and `biome check .` with zero diagnostics.** A suppression comment requires a written justification; an unexplained one is a defect.
- **Vitest runs in pure-Node mode** (no `@cloudflare/vitest-pool-workers`) as long as the code under test touches no Workers-runtime primitive an interface-shaped fake cannot cover. **The dividing line is not "is this file in `src/`" — it is whether the code genuinely needs a Durable Object, an `ExecutionContext`, a real binding, or a similarly un-fakeable runtime primitive to behave correctly.** Code that truly needs the runtime (the `McpAgent` lifecycle, the Access-JWT flow) may legitimately have no automated coverage, with manual/Inspector testing as the acknowledged strategy — **do not paper that over with a Node-mode unit test that cannot meaningfully exercise it**, and do not switch the whole suite to the Workers pool to chase one such case.
- The sanctioned dependency-mocking idiom is `vi.hoisted` + `vi.mock` class replacement with `beforeEach(vi.clearAllMocks)` where there is an injected dependency to swap; mocking `fetch` directly is the correct alternative where there is not. (Stated so the rubric reads identically for both sides — the developer never writes tests; `tests-developer` does.)
- **The one sanctioned test-side cast is `as unknown as Env`, never a bare `as Env`** — this standard's own convention for the generated Workers `Env` type, not a project-specific habit.
- `wrangler deploy --dry-run` is the only thing that actually bundles the Worker — type-checking does not. Treat a clean dry-run as part of "compiles."
