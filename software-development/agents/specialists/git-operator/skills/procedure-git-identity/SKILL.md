# Procedure: Git Signing Identity

The **one** gate every commit and signed tag passes first. A signature and a `Signed-off-by` are only meaningful if the **committer identity, the signing key, and the sign-off are one consistent, reconciled identity** — this skill makes that deterministic and requires the user's confirmation.

## The four fields that must reconcile

For a commit to be both **"Verified"** on GitHub and validly signed-off, these must agree:

1. **`git config user.email`** — the **committer** email. Must be an email **verified/confirmed on the hosting account** — GitHub-verified (else the commit is unattributed and cannot be "Verified") or GitLab-confirmed. This is asserted only when the platform query **succeeds**: a `verified` result confirms it and an `unverified` result fails the gate, but an **undetermined (`unknown`) or `skipped`** check leaves the question unasked and **does not fail the gate**. The check is **per-platform and independent** — `--github` for a GitHub remote, `--gitlab` for a GitLab one — and each reports its own one of those four states.
2. **The signing key's email** — the GPG key's UID email, or the SSH allowed-signers entry — must match (1).
3. **`Signed-off-by:` email** — the DCO footer the commit will carry — must match (1).
4. **Committer vs author** — distinct; if they differ (applying someone else's patch), that is surfaced explicitly so it is intentional, not accidental (a mismatch downgrades the badge to "Partially verified").

Signing method is **GPG or SSH** — both earn "Verified"; the script handles whichever `gpg.format` is configured. (Sigstore/`gitsign` is CI-only today — GitHub shows it "Unverified".)

Enable **Vigilant Mode** on the account so *unsigned* commits are flagged "Unverified" rather than passing unmarked (account-scope — complements the repo ruleset's "require signed commits"). Maintain a **`.mailmap`** to canonicalize author/committer names + emails in `git log`/`shortlog` — it complements this identity discipline.

## The procedure (the operator follows this)

1. **Run** `$HOME/.claude/skills/procedure-git-identity/scripts/resolve-identity.sh` from the repository, passing **the flag that matches the repo's remote** — `--github` for a GitHub remote, `--gitlab` for a GitLab one. It reads the git config + key material and reconciles the fields above — no guessing by the model. **Always pass the matching flag** — it is what surfaces an unattributable committer email. Do not decide for yourself whether to include it. The two flags are independent and may both be passed if the backend is genuinely not yet known; on a normal single-remote repo, pass exactly the one that matches.
   - **With `--gitlab`, pass `--gitlab-host HOST` whenever you know the target instance** (e.g. `--gitlab-host gitlab.com`, or the self-managed hostname) — it is what makes a *definite* answer possible at all. **Unpinned, `--gitlab` is CAPPED at `unknown`/`skipped` and never reports `verified` or `unverified`:** `glab` would pick its instance from ambient state (the cwd's git remote, an inherited `$GITLAB_HOST`, its own config, else gitlab.com), and both definite states are claims about *one specific account* that such a resolution cannot back up. The script warns, makes no API call, and reports `unknown`. So passing **both** `--github` and `--gitlab` when the backend is genuinely unknown stays safe — the speculative side yields `unknown`/`skipped`, never a wrong definite answer — but the moment you *do* know it is GitLab, pin the host or you get no answer.
   - **The host you pin must come from the ACCOUNT GATE, never from a repo's remote URL.** Use the host `procedure-gitlab-auth` confirmed the user is authenticated to — the same provenance `find-mr.sh`'s `--confirmed-host` requires. A handed-over or cloned repository's remote can point at an **attacker-controlled instance**, whose `/user` response trivially manufactures a `verified`; the script validates the host's *shape*, and cannot validate its *trustworthiness*. If you have no gate-confirmed host, run `--gitlab` unpinned and report the `unknown` — never substitute a host you read off an untrusted remote.
   - **A spurious block is possible, so do not treat `unverified` as beyond question.** The design keeps it rare — only a query that *succeeded and answered no* is fatal, and a query that could not run is a notice (`unknown`/`skipped`, exit 0). The **wrong-instance** path is now closed by construction (unpinned can no longer *produce* a definite answer), which leaves one residual: an **address form the matcher does not cover** — notably GitLab's private commit address (`ID-username@users.noreply.gitlab.com`), which GitLab accepts on a commit but which neither checked endpoint reports. A pinned-but-*wrong* host is also still possible if the pin's provenance was not the account gate. The operator **reports the state; it does not assert that a negative is the user's fault.** On `unverified`, stop as required by step 2, and say which of these could explain it.
2. **If it exits non-zero** (field mismatch, missing/misconfigured signing key, or a `--github`/`--gitlab` check that returned a real negative), STOP — do not commit. Report exactly what failed and what the user must fix. Branch on the **exit status**, never on how a state's name reads: a check that could not run exits `0` and is a notice, not a stop.
3. **If it exits zero**, present the resolved identity using **the report template below** — filled verbatim from the script's machine-parseable `IDENTITY_*` output — and **ask the user to confirm this is the identity + key to use.**
4. **If the user does NOT approve** the proposed identity and/or signing key, do NOT commit — **switch using the scripts** (never by improvising git commands):
   - Run **`$HOME/.claude/skills/procedure-git-identity/scripts/list-identities.sh`** to enumerate the available signing identities/keys (GPG secret keys + SSH signing keys) and present the choices.
   - Once the user picks, run **`$HOME/.claude/skills/procedure-git-identity/scripts/switch-identity.sh`** to apply it deterministically (repo-local by default; `--scope global` to persist).
   - Re-run **`$HOME/.claude/skills/procedure-git-identity/scripts/resolve-identity.sh`** with **the same remote-matching flag** (`--github` or `--gitlab`) to confirm the new selection reconciles, then present it again for confirmation. The re-check carries that flag too — a switch changes the committer email, so it is exactly when the platform question needs re-asking.
   - Repeat until the user confirms, or abort on request. Never commit with an identity/key the user did not approve.
5. **Commit only after the user confirms.** This confirmation gate is mandatory (the user's rule); it is never skipped or assumed.

## The identity report (present EXACTLY this at step 3)

Render this block as live Markdown, filled from `resolve-identity.sh`'s `IDENTITY_*` lines — substitute each `{KEY}` with that line's value **verbatim**; never reorder, reformat, or drop a row. This fixed shape is what the user confirms against, so it must be deterministic run-to-run:

```markdown
### 🔑 Signing identity — confirm before I commit

| Field | Value |
|-------|-------|
| Name | {IDENTITY_NAME} |
| Committer email | {IDENTITY_COMMITTER_EMAIL} — {platform_note} |
| Signing method | {IDENTITY_SIGNING_METHOD} |
| Signing key | {IDENTITY_SIGNING_KEY_ID} · {IDENTITY_SIGNING_KEY_FPR} |
| Sign-off | {IDENTITY_SIGNOFF} |
| Author vs committer | {author_note} |

**Reconciliation:** {reconciliation_note}

{platform_unknown_notice}

**Commit under this identity?** Reply **yes** to proceed, or **switch** to choose another.
```

**Rendering rules for the derived cells (map the exact value → text):**
- `{platform_note}` ← the **platform status line whose flag you passed**: `IDENTITY_GITHUB` (for `--github`) or `IDENTITY_GITLAB` (for `--gitlab`). Both lines are always printed, but the one whose flag you did **not** pass always reads `skipped` — render only the one you asked for.
  - From `IDENTITY_GITHUB`: `verified` → "✅ GitHub-verified" · `unverified` → "⚠️ NOT GitHub-verified" · `unknown` → "❓ GitHub verification undetermined (the check could not run — not a failure)" · `skipped` → "ℹ️ GitHub check skipped (gh absent or unauthenticated)".
  - From `IDENTITY_GITLAB`: `verified` → "✅ GitLab-confirmed" · `unverified` → "⚠️ NOT GitLab-confirmed" · `unknown` → "❓ GitLab confirmation undetermined (the check could not run — not a failure)" · `skipped` → "ℹ️ GitLab check skipped (glab or jq absent, or glab unauthenticated)".
  - If you passed **both** flags (backend genuinely unknown), render both notes separated by " · " — never silently drop one.
- `{author_note}` ← `IDENTITY_AUTHOR_COMMITTER_MATCH`: `true` → "✅ author = committer" · `false` → "⚠️ author {IDENTITY_AUTHOR_EMAIL} ≠ committer — applying another's patch".
- `{reconciliation_note}` ← `IDENTITY_STATUS`: `reconciled` → "✅ committer = signing-key = sign-off — consistent" · `mismatch` **with `IDENTITY_GITHUB=unverified`** → "❌ committer email is not GitHub-verified — I will NOT commit" · `mismatch` **with `IDENTITY_GITLAB=unverified`** → "❌ committer email is not GitLab-confirmed — I will NOT commit" (in both platform cases the three git-local fields DO agree; naming them as the cause misreports it) · `mismatch` otherwise → "❌ fields disagree — I will NOT commit".
- If a key's value is empty, render `—` (never invent one). If `IDENTITY_STATUS=mismatch` **or** the script exited non-zero: present the block, name the failing field, and STOP — do **not** offer "yes".
- `{platform_unknown_notice}` ← the platform status line you passed: `verified`/`unverified`/`skipped` → render **empty** (the line disappears) · `unknown` → the prose notice below. It is a placeholder precisely because it is the one element guarding a fail-open: every other derived cell is wired into the fixed template, and the notice must be too. If both flags were passed and both are `unknown`, render both notices.
- **A platform status of `unknown` — surface it in PROSE, never only as a table glyph.** The commit is *not* blocked and `{reconciliation_note}` will still read "consistent", so the ❓ cell alone is too quiet to be the sole notice on a fail-open. Render `{platform_unknown_notice}` as one sentence naming what went unchecked and relaying the script's remedy **verbatim**:
  - `IDENTITY_GITHUB=unknown`, e.g.: "⚠️ I could not confirm this email is GitHub-verified (`gh api user/emails` failed — candidate causes: the token lacks the `user` OAuth scope, a network failure, or a rate limit). If it is the scope, fix it with `gh auth refresh -h github.com -s user`. This does not block the commit."
  - `IDENTITY_GITLAB=unknown`, e.g.: "⚠️ I could not confirm this email is GitLab-confirmed (`glab api user/emails` failed — candidate causes: the token lacks a scope that can read the account's email addresses (`read_user` or `api`), a network failure, or a rate limit). If it is the scope, re-authenticate with `glab auth login`. This does not block the commit." **`unknown` now also covers two cases where the script deliberately did NOT query** — relay whichever warning it actually emitted, because the remedy differs: **no `--gitlab-host`** ("the result is capped at `unknown`; re-run with the gate-confirmed host for a definite answer") and **TLS verification disabled** for the pinned host ("a `verified` could be manufactured by an on-path attacker; re-enable it with `glab config set skip_tls_verify false`"). Both are notices, not blocks — but both mean the platform question is genuinely *unanswered*, so never present them as a soft pass. *(The GitLab path makes **two** calls — `glab api user/emails` for the secondary addresses and `glab api user` for the primary — and reports `unknown` when EITHER failed, returned a blank body, or returned a body that did not parse. It therefore may emit **more than one** warning sentence: relay each one the script actually emitted, verbatim, and do not collapse them into a single generic notice — they name different endpoints and different remedies.)*
  - **Relay the script's second warning line (`gh reported: …` / `glab reported: …`) too when it emitted one — that is the CLI's own message and names the real cause.** Then still offer **yes** — this is a notice, never a gate. Repeat it on every commit while the state persists; a permanently-scoped-out token must not go quiet.

## The script suite (`$HOME/.claude/skills/procedure-git-identity/scripts/` — deterministic & portable)

All identity operations run through these scripts — the operator **never improvises git commands** for identity/signing. **Invoke each by its deployed absolute path — `$HOME/.claude/skills/procedure-git-identity/scripts/<name>`.** Never a bare `scripts/<name>` (it resolves against the repo cwd, where the script does not exist), and never `${CLAUDE_SKILL_DIR}/…` from the operator's Bash — that placeholder is substituted only inside a skill's own `SKILL.md` content at invocation, NOT in the shell the operator runs, so it will not resolve there. All are **highly portable** (POSIX `sh`, any machine with `git` + a signing tool), **deterministic**, and `shellcheck`-clean; all are read-only **except `switch-identity.sh`, which writes only git config** (never keys or the repo tree).

**`resolve-identity.sh`** `[--email/--name/--signingkey/--format]` `[--github]` `[--gitlab]` `[--gitlab-host HOST]` — reconcile & report (read-only):
- Reads `git config user.name/user.email/user.signingkey/gpg.format` (default `openpgp`), the committer/author identity, and the key material — GPG (`gpg --list-secret-keys`) or SSH (`gpg.ssh.allowedSignersFile`).
- **Override flags** reconcile a SPECIFIED identity instead of the configured one (used to re-verify a switched choice), still read-only.
- Reconciles fields 1–3; surfaces field 4 (author≠committer) as a warning.
- **`--github`** (optional): if `gh` is present + authenticated, also verify `user.email` is a **GitHub-verified** address (`gh api user/emails`). Four states, and **only `unverified` is fatal**: `verified` (query succeeded, email listed) · `unverified` (query **succeeded** and did not list it — a real negative, exit 1) · `unknown` (the query **failed** — missing `user` OAuth scope, network, rate limit — **notice, never fail**; remedy: `gh auth refresh -h github.com -s user`) · `skipped` (gh absent/unauthenticated — **notice, never fail**). A question that could not be asked is never answered "no"; the git-local checks always run regardless.
- **`--gitlab`** (optional): the structural counterpart for a GitLab remote — if `glab` **and `jq`** are present and glab is authenticated, also verify `user.email` is a **GitLab-confirmed** address. **The same four states, the same "only `unverified` is fatal" rule, and the same never-report-a-failed-query-as-a-negative discipline**: `verified` · `unverified` (**both** queries succeeded, parsed, and neither listed it — a real negative, exit 1) · `unknown` (**either** query failed, returned a **blank body**, or returned a body that **did not parse** as its expected shape — **notice, never fail**; remedy: `glab auth login`) · `skipped` (glab or jq absent, or glab unauthenticated — **notice, never fail**). **The two definite states require `--gitlab-host`** — see below.
- **`--gitlab-host HOST`** (optional, requires `--gitlab`; bare hostname, optional `:port`, **no scheme**): pins the instance the check queries by exporting `GITLAB_HOST` before **both** the auth check and every API call, and is what **unlocks a definite answer**. **Unpinned, `--gitlab` is capped at `unknown`/`skipped` — it can never return `verified` or `unverified`**, and makes no API call: glab would resolve the instance from ambient state (cwd git remote → `$GITLAB_HOST` → glab config → gitlab.com), and both definite states are assertions about *one specific account* that an ambient resolution cannot support. Reporting `unknown` is the same "never assert on a channel that cannot support the assertion" rule the state machine already applies to a failed query — an untrustworthy answer is worth less than no answer. The flag stays **optional** (unlike `find-mr.sh`'s `--confirmed-host`, which is **required** because it guards a *write*) precisely so a caller that does not yet know the backend can pass `--github` **and** `--gitlab` speculatively; the cap is what makes that safe.
  - **Provenance is a caller contract the script cannot enforce:** pass only a host the **account gate (`procedure-gitlab-auth`) confirmed** — identical provenance to `find-mr.sh`'s `--confirmed-host`. **Never read the host off an untrusted repository's remote URL** (a handed-over or cloned repo can name an **attacker-controlled instance** whose `/user` response manufactures a `verified`). The validator — deliberately the *same name and body* as the siblings' `is_valid_confirmed_host`, so all copies stay greppable as one family — checks the value's **shape only**. An invalid host, or the flag without `--gitlab`, is a **usage error (exit 2)** — never confusable with exit 1's "do not commit".
  - **TLS verification is checked, not assumed:** if glab is configured to skip TLS certificate verification for the pinned host (`skip_tls_verify`, in the env, local, global, or per-host config), a `verified` could be manufactured by an on-path attacker — so the result degrades to **`unknown`** with a warning naming TLS as the reason, and no query is made.
  - **`--github` and `--gitlab` are INDEPENDENT parallel code paths, deliberately not unified** behind one generic "platform" flag — this mirrors the framework's existing GH/GL split (`procedure-gh-pr` / `procedure-glab-mr`: parallel scripts and flags, not a premature abstraction). Either, both, or neither may be passed; each computes and prints its own status, and the machine block always carries **both** `IDENTITY_GITHUB=` and `IDENTITY_GITLAB=` (the one whose flag was not passed reads `skipped`).
  - **`--gitlab` makes TWO API calls where `--github` makes one, because GitLab splits the account's addresses across two endpoints.** `GET /user/emails` returns **only the additional (secondary) addresses — the account's PRIMARY address is NOT in that list** (the endpoint presents `current_user.emails`; GitLab's own `User#verified_emails` has to prepend the primary from the `users.email` column before concatenating it). GitHub's `/user/emails` *does* include the primary, so a one-call port of the `--github` logic reported `unverified` for the single most common configuration — `user.email` **is** the account's primary address — and refused the commit on essentially every real GitLab repo. The primary is therefore resolved separately from **`GET /user`** (its `.email` + top-level `.confirmed_at`), which is a single object: no `--paginate`, different filter. The primary probe **short-circuits** when the secondary list already answered `verified`. A probe that **could not answer** contributes `unknown`, never a negative — so a failed secondary check can never manufacture a false negative for an address that lives on the primary path.
  - **The GitLab comparison is case-INSENSITIVE; the GitHub one is not.** GitLab down-cases the addresses it stores (Devise `case_insensitive_keys`), so a mixed-case `git config user.email` (`First.Last@corp.com`) would never match its own confirmed `first.last@corp.com`. GitHub returns addresses in their **registered** form and the local part of an address is case-sensitive per RFC 5321, so that path deliberately keeps an exact compare (pinned by a test).
  - **Why the mechanics differ even though the contract does not:** `glab api` has **no `--jq` flag** (unlike `gh api`, and unlike `glab mr list`), so filters run in an **external `jq`** — which is why `jq` is a precondition on this path and its absence is a `skipped`. GitLab also marks a confirmed address with a non-null **`confirmed_at` timestamp** rather than GitHub's boolean `verified` field.
  - **Known residual gap (not covered by either endpoint):** GitLab's **private commit address** (`ID-username@users.noreply.gitlab.com`) is accepted on a commit but is reported by neither `/user/emails` nor `/user`'s `.email`, so a `user.email` set to it will read `unverified`. Treat that as a candidate explanation when a block looks wrong.
- Output: human-readable identity block **+ machine-parseable `KEY=VALUE`** on stdout; diagnostics on stderr. Exit `0` reconciled · `1` mismatch/misconfig · `2` usage.

**`list-identities.sh`** — enumerate available signing identities so the user can choose (read-only):
- Lists GPG secret keys (key id, fingerprint, UID name + email) and SSH signing keys, in a **stable, deterministic order**.
- Output: a numbered human-readable list + a machine-parseable form. Exit `0`, or `1` if none found.

**`switch-identity.sh`** `--email <e> --name <n> --signingkey <k>` `[--format gpg|ssh]` `[--scope repo|global]` — deterministically APPLY a chosen identity/key:
- Sets `user.name/user.email/user.signingkey/gpg.format` via `git config` — **`--scope repo` (default, local)** or `--scope global`. Validates the key exists before setting; **idempotent** (same args → same config).
- Exit `0` applied · `1` invalid/missing key · `2` usage. The operator then re-runs `resolve-identity.sh` — with the same remote-matching `--github`/`--gitlab` flag — to confirm.

**Shared portability contract:** POSIX `sh` only (no bashisms), macOS (BSD / Bash 3.2) **and** Linux, `shellcheck`-clean, `command -v` guards for every external binary.

**Graceful degradation applies to the OPTIONAL PLATFORM binaries only — `gh`, `glab`, and `jq`.** Their absence degrades that platform check to a non-fatal `skipped` (exit 0), because the platform question is an *additional* assurance on top of the git-local reconciliation. **A missing SIGNING tool is exit 1, not a `skipped`**, because without it the identity cannot be reconciled at all and there is nothing to report: `gpg.format=openpgp` with no `gpg` on `PATH` is fatal, as is an unset `gpg.ssh.allowedSignersFile`, an allowed-signers file that is missing, or one that does not contain the signing key. (`ssh-keygen` is the one exception on the ssh path: it is used only to render a fingerprint, so its absence just leaves that field empty.) Each script ships with portable tests (see `tests/`).

## Constraints (NEVER violate)
- Never commit or cut a signed tag without a green run of the script **and** the user's confirmation.
- Never proceed on a field mismatch, a missing signing key, or an author≠committer divergence the user hasn't acknowledged.
- The script never modifies git config or the repo — it only reads and reports.

*Changed in 1.1 — GitLab parity for the platform email check.* `resolve-identity.sh` gains a **`--gitlab`** flag, the structural twin of `--github`: the same four states (`verified`/`unverified`/`unknown`/`skipped`), the same **only-`unverified`-is-fatal** rule, and the same discipline that a query which could not run is never reported as a negative. It is an **independent parallel code path**, not a unification of the two behind a generic "platform" flag — matching the framework's existing GH/GL split. New machine-parseable line **`IDENTITY_GITLAB=`** (always printed, alongside `IDENTITY_GITHUB=`) plus a parallel annotated human-readable line. The report template's `{github_note}`/`{github_unknown_notice}` generalize to **`{platform_note}`/`{platform_unknown_notice}`**, rendered from whichever flag was passed. **Removed** the previous "there is deliberately no `--gitlab` counterpart yet" gap disclosure — the gap is closed. Callers now pass the flag matching the repo's remote rather than `--github` unconditionally-or-not-at-all.

*Changed in 1.2 — correctness fixes to the `--gitlab` path, plus two honesty corrections to this document.* The `--gitlab` check now makes **two** API calls: `GET /user/emails` returns only the account's **secondary** addresses, so the previous single-call implementation reported `unverified` — and refused the commit — whenever `user.email` was the account's **primary** address, i.e. on essentially every real GitLab repo. The primary is now resolved from `GET /user`, and a probe that could not answer contributes `unknown` rather than a false negative. The GitLab comparison is now **case-insensitive** (GitLab down-cases stored addresses; the GitHub path deliberately stays exact). New optional **`--gitlab-host HOST`** pins the queried instance, closing a path where the reported status could describe a different account than the one being reconciled: **an UNPINNED `--gitlab` is now capped at `unknown`/`skipped` and can never report `verified`/`unverified`** (both are claims about one specific account that glab's ambient instance resolution cannot support), which is what keeps "pass both flags when the backend is unknown" safe while leaving the flag optional. Pinning additionally requires **account-gate provenance** (never a host read off an untrusted repo's remote — documented as a caller contract, since the validator can only check shape) and now **checks `skip_tls_verify`**, degrading to `unknown` rather than trusting an unverified channel. Values printed into the machine-parseable block are validated against **control-character injection** (a `user.name`/`user.signingkey`/author-email newline could otherwise forge `IDENTITY_*` lines), and every fixed-string match passes its pattern via `grep -Fxq -e` so a leading-dash address can never be read as a grep option. **Corrected here:** the claim that the platform flags "cannot block you spuriously" (they can — two residual paths are now named), and the claim that a missing `gh`/`glab`/`jq`/**`gpg`**/`ssh` all degrade to `skipped` (only the three optional *platform* binaries do; a missing signing tool or allowed-signers file is exit 1).
